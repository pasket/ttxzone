# After-action report and improvement plan

The exercise's editable after-action report (AAR) and improvement plan, written after the session from what it recorded. Code: `models/after_action.py`, `services/after_action_service.py`, `endpoints/after_action.py`; frontend `components/aar/` (`AfterActionSection`, `ActionDialog`, `lib/aar.ts`). Tests `test_after_action.py`, `AfterActionSection.test.tsx`.

## Who
- **Writes**: the exercise's Planners (`plans`) and its Lead Evaluator (`TTXAccess.leads` on an evaluator) — `can_write`; checked by the `_author` dependency before the body (like a design route: 403 `TTX_ACCESS_DENIED`).
- **Reads**: those, its Controllers and the organization's Program Managers (`can_read`); anyone else 403.
- Screens: Creator → After-action report (`after-action`, after the Session plan), Playground → After-action report for Evaluators (the Lead Evaluator edits, others are told they can't read it), Control → After-action report (read-only). One component, `can_edit` from the API.
- **From the session** (after Conclusions, for the authors and Controllers — `can_see_session`; not a Program Manager off the team): the feedback form's aggregates (`FeedbackResults`) and the team's notes (`TeamNotesPanel`) of the run the report was written from (`run_id`, read with `?run=` so a later restart doesn't swap them), to draw on while writing; never copied into the report.

## Lifecycle
- Before it exists the screen previews it (`AarPreview`, from `GET /ttx/{id}/aar/preview`): the report's parts over the exercise's objectives — the run's plan, else the latest Session plan, else the needs analysis — each marked filled from the session or written by the authors; Start shows only to authors and is disabled until the session has started.
- `POST /ttx/{id}/aar` `{run_id?}` starts it once a session has been held (409 `RUN_NOT_STARTED`, `AAR_EXISTS`; 404 `RUN_NOT_FOUND` for a run of another exercise), from the run chosen -- by default the current one, else the latest archived, so a restart before writing it doesn't lose the chance. The preview lists them (`runs`, the default first) and offers a choice when there are several. It's **seeded from that session**: executive summary and scenario from the MSEL snapshot; per EEG objective of the run's plan the most frequent level rated (`overall`), points rated P/S as strengths and M/U — plus expected actions marked partial / not observed — as areas for improvement, each as `- point — why (evaluator)` lines to edit; the table's decisions as `- decision — inject` lines in the analysis of each objective their inject serves (the inject's `objective_ids` in the MSEL snapshot), those on an inject serving none in the conclusions. No actions are seeded.
- `POST /ttx/{id}/aar/run` `{run_id, revision}` writes it from another session (the screen's "Change session", for authors when there are several; the AI assistant's pending proposals for it are discarded): what's written stays — summaries, objectives' text and level, conclusions, actions —, the session's ratings, feedback and notes beside it and its PDF become that run's, and it reopens a FINAL report like any edit (`AAR_STALE`, `RUN_NOT_FOUND`). Its objectives follow that run's plan: the ones it adds come seeded from it, the ones it drops go if nothing was written in them and no action cites them, else 409 `AAR_OBJECTIVES_IN_USE` naming them. The run it leaves can then be deleted.
- `PUT /ttx/{id}/aar` saves the whole report (autosaved ~1 s after typing; optimistic `revision`, 409 `AAR_STALE`). Objectives are the plan's (only level and text change); actions are full-replace keyed by id, new ones get the next `IP-NN` (never reused).
- `POST /aar/transitions` `{to: final|draft}` (no step-up; recorded as `exercise.aar_final`/`exercise.aar_reopened`): FINAL stamps who/when and freezes an `AfterActionSnapshot`; any later edit reopens it as version N+1.
- `PATCH /aar/actions/{code}` (`{status, status_note, due_date}`): following the plan up — never reopens a FINAL report. An action is **overdue** when its due date has passed and it isn't done or cancelled.
- `GET /aar/export.pdf?lang=`: the report and plan as written, TLP-labelled, EXERCISE band, DRAFT until final (`run_export_service.render_report_pdf`). The session's automatic draft (`/run/export/aar.pdf`) stays separate.

## Model
- `AfterActionReport` (one per exercise; `run_id` — the run it was written from: it stays on it when a restart archives that run, its PDF reads that run, and that run can't be deleted; chosen when it's started, changeable afterwards —, status, version, revision, executive summary, scenario, conclusions, `next_action_number`, finalized by/at), `AfterActionObjective` (objective code and title, `overall` P/S/M/U, strengths, improvements, analysis; the session's ratings come along read-only), `ImprovementAction` (code, objective code, finding, action, **owner and area as free text** — owners are often people without an account —, due date, status OPEN/IN_PROGRESS/DONE/CANCELLED, status note), `AfterActionSnapshot`.
- Deleted with the exercise, before its run (`delete_reports_for_ttx`).

## AI assistant
Its authors can draft the report with an AI client, which reads the session and proposes text and actions, each citing what backs it, for them to accept on the page. It never proposes a level or an action's follow-up: `docs/features/ai-assistant.md#after-action-report`.

## Re-tested by a later exercise
- An action can name the later exercise that tests it again, and optionally which of its objectives (`ImprovementAction.retest_ttx_id` / `retest_objective_id`). Follow-up, like the status: set through `PATCH …/aar/actions/{code}` (only when `retest_ttx_id` or `retest_objective_id` is sent; null clears), never reopens a FINAL report, works on an archived exercise; or by a Program Manager in Admin → Improvement plan (`PUT /organizations/{id}/improvement-plan/{action_id}/retest`). Rules (`after_action_service._link_retest`): the target is an exercise of the same organization created after the report's (422 `RETEST_INVALID_EXERCISE`); the objective is one of that exercise's needs analysis (`RETEST_INVALID_OBJECTIVE`). An archived target is allowed.
- Choosing (`aar/RetestDialog`, from the plan table's **Re-tested in** column for `can_follow_up`, and from Admin's): `…/retest-candidates` lists each later exercise's code, name and objectives — **deliberately nothing else**, since whoever links it may hold no seat on that exercise.
- Shown as `ImprovementActionRead.retest` / `ImprovementPlanRow.retest` (`RetestRead`: exercise code and name, objective code and title; `aar/RetestRefCell`), in the report PDF under the action ("Re-tested in …"), and on the later exercise: `GET /ttx/{id}/retests` (`RetestsPanel`, read-only, hidden when empty) in its Needs analysis → Objectives step and its after-action report (preview and report, above its own plan), so its authors write the result against them; the status is still followed up on the source action.
- Unlinked, never deleted, when the target goes: deleting the exercise clears both (`ttx_service.delete_exercises`); an objective removed from its needs analysis, a scenario copied over it or its needs form deleted clears only the objective (`ttx_needs_form_service.release_retest_objectives`).

## Admin → Improvement plan
- `AdminImprovementPlanSection` (`/admin/improvement-plan`): every action of the organization's reports, soonest due first, filtered by status, overdue, re-test (linked / not yet) or text, with a **Re-tested in** column the Program Manager links from (`GET /organizations/{id}/improvement-plan`); each row offers its exercise's report as PDF (a Program Manager reads it without being on the exercise).
- The Admin dashboard's KPI strip adds open actions and how many are overdue (`DashboardKpis.improvement_open` / `improvement_overdue`).
