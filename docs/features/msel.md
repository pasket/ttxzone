# Creator → MSEL (Master Scenario Events List)

The timed injects that drive the session, built from the approved objectives: every inject evaluates ≥ 1 objective through its **expected actions**, which are the EEG's observation points. ATT&CK data, threat actors and release conversion: `docs/architecture/attack.md`.

## Backend
Files: `app/models/ttx_msel.py`, `app/models/inject.py`, `services/ttx_msel_service.py`, `endpoints/ttx_msel.py`; tests `test_ttx_msel.py` + the sample MSEL in `tests/msel_helpers.py`.

### Model
- `TTXMsel` — 1:1 with `TTX`: scenario fields, `status` (draft / in_review / ready), `version`, `revision`, `needs_form_version`, `attack_version`, never-reused code counters, `exercise_start` ("Session start"), `incident_start` ("Scenario start": when the incident begins inside the fiction), `incident_date` ("Scenario date", optional: the Playground's clock reads it, else "Day N"), duration, `time_compression`, `ready_by`/`ready_by_id`/`ready_at` (who marked the current version READY).
- `MselPhase` (+ `MselPhaseObjective`, whose `due` flag makes the phase's end a deadline of that objective -- `PhaseInput.due_objective_ids`, a subset of `objective_ids`; the EEG lists them as `due_phases`, in place of a minutes time box): session band (`offset`/`end_offset`), `headline` (≤ 80, optional: the line the table sees once the phase begins in the Playground's phase track), key questions, situation update, `incident_jump_minutes` (≤ 30 days; ignored for a phase at T+0).
- `MselSimulatedActor` — the cast, owned by the **exercise** (`ttx_id`), not the MSEL; free-text `played_by`. See `docs/features/library.md`.
- `Inject`: phase, `kind` (mandatory / contingent), `offset_minutes` (session minutes) or trigger + purpose + `fires_at_minute` (contingent only, minutes after its phase starts: when the facilitator checks; null = the trigger action's window), `format` (`inject`; `discussion`: a debrief or reflection prompt, no objective, stays out of the EEG and coverage; `poll`: `poll_question`, 2–6 `poll_options` the Players vote on and, by position, optional `poll_outcomes` (≤ 1000 characters: what follows each option), also outside the evaluation, no expected actions, no sender or audience; coded `INJ-NN`, `DSC-NN` or `POL-NN`, see Codes), sender actor, recipients, delivery method, ATT&CK attribution + techniques, facilitator notes, review status, `validated_by_id`/`validated_by`, `origin`/`origin_id`/`origin_name`. MSEL columns are nullable in the DB, required by the schemas. With `InjectObjective` and `InjectExpectedAction` (its `description` *is* the observation point; code `INJ-NN-AN` is positional, the id is the stable reference; `objective_ids` — no FK, migration `b5e8d1f4a273` backfilled every action with its inject's — is the subset of the inject's objectives it evidences: only their EEGs list it. The payload's `null` means all of the inject's (library inserts, older clients), others are dropped, an inject of another format clears them; reads keep only those still on the inject, and snapshots frozen before the field read as all of the inject's, `schemas/ttx_msel.action_objective_ids`).
- Validation of a poll: M27 `POLL_INCOMPLETE` (blocking) — a question and at least two different options, none blank. M28 `POLL_OUTCOME_MISSING` (warning) — only some options say what follows, so the table may land on one with no consequence. M29 `METER_INCOMPLETE` (blocking) — an impact meter without a name of its own. M30 `METER_UNUSED` (warning) — no poll moves a meter. Its context text is optional, and the sender and audience rules skip it.
- **Impact meters**: `TTXMsel.meters` (`[{key, name}]`, up to 6, Scenario tab → `MetersField`) are what the polls' decisions add up on; `Inject.poll_impacts` says, by option, what each adds to each (meter key → 1 low, 2 medium, 3 high; none is left out), with a select per meter under each option. A meter that goes takes its impacts with it (`MselSaveRequest`). Both freeze in the READY snapshot.
- A poll's outcomes print in the team's documents (MSEL and Facilitator guide), never on the inject cards. The dialog's Question and options step edits each one under its option, and an option moves or goes with its outcome.
- `MselSnapshot` — JSONB, frozen when READY (names resolved, codes frozen).
- **Codes**: `PH-NN`, `ACT-NN`, `THR-NN`, and **one number series for every inject**, mandatory or contingent; a kind change keeps the code. An inject of the `inject` format is `INJ-NN`, a **poll** `POL-NN`, a **discussion** inject (labelled "Discussion" in the inject dialog, the Injects list and the PDFs) `DSC-NN`: switching the format keeps the number and moves the prefix (`_recoded` in `save_msel`), its actions follow (`DSC-04-A1`) and the codes named in the MSEL's free text are rewritten in the same save (`_rewrite_codes`); the draft adopts the server's codes (`adoptSavedIds`). Renumbering keeps each inject's prefix on the shared series. A discussion inject saved before the prefix existed takes `DSC` on its next save; READY snapshots keep their codes. (Old `INJ-Cxx` codes were renumbered by migration `b3f1c2d4e5a6`; READY snapshots keep theirs, so `CODE_PATTERN` still recognises `INJ-Cxx`.) Codes are never reused, so a deletion leaves a gap. **Renumbering**: while the MSEL is a draft, `POST …/msel/renumber` (`kind`: `phases` by start, `injects` in storyline order -- mandatory ones by T+, each followed depth first by the contingent injects that branch off it, siblings in creation order, untimed and loose ones last (`_storyline_order`), `threat_actors` in list order) rewrites that kind's codes, resets its counter, makes expected actions follow (`INJ-01-A1`) and rewrites the codes named in the MSEL's free text in one pass (`app/services/code_renumber.py`); `codes` (row id → code, the `previous` it returned) undoes it (Undo toast). A draft that was READY before (it has `msel_snapshot` rows) needs `confirm_frozen: true` (`409 MSEL_RENUMBER_CONFIRM` otherwise, undo included): `MselRead.frozen_versions` lists those versions (version, ready date and person, sessions played from each), and the button opens a confirmation naming them and warning that their codes, and those of the sessions, EEGs, reports and PDFs made from them, stop matching the draft's. Snapshots are never rewritten. `MselRead.renumberable` lists the kinds out of order; the Phases, Injects and Threat actors headers then show the button (disabled while unsaved: the server renumbers what's saved, and the Phases history is reset). A phase whose code number isn't its place in the session says "N of M in the session" under it.

### Lifecycle
- **Created lazily** on the first `GET` with an APPROVED needs form (row-locked on the form; seeds the cast — 7 neutral actors in the request locale, plus the 2 NCCS actors when the form names NCCS); 409 `NEEDS_FORM_NOT_APPROVED` otherwise.
- **Editable only while the needs form is APPROVED** — else `editable: false` and every write is 409 `NEEDS_FORM_NOT_APPROVED`.
- Same save model as the needs form: whole-MSEL `PUT` (full replace keyed by id; new rows referenced by payload `key`: `phase_key`, `actor_key`, …), `revision` optimistic lock (409 `MSEL_STALE`). 422 only for what can't be stored (unknown objective/phase/actor/ATT&CK references; limits 8 phases, 40 injects, 8 expected actions per inject). Everything else is the validation report.
- `POST …/msel/validate` = dry run (unknown objectives reported as `UNKNOWN_OBJECTIVE`).
- Transitions (`POST …/msel/transitions`): report `ready` empty → draft → in_review; `approved` empty (incl. M12 mandatory injects validated) → ready, which writes a `MselSnapshot` and stamps who did it, server-side like an inject's validator (`ready_by` = the name then, `ready_by_id`, `ready_at`; no step-up: it's a reviewer's sign-off, like validating an inject). Any edit past draft returns to draft and clears the stamp; leaving READY opens version N+1. A deleted account's stamp reads "Deleted user".
- Review tab (`ReviewStepNote`): under the buttons, the requirement (`submitHint`/`readyHint`) shows only while it disables the next step; otherwise a green note says nothing blocks it (`submitOk`, or `submitOkPending` when injects are still to validate; `readyOk`). Once READY: "Marked ready by {name} · {date}".
- **M02**: when the needs form is approved again with another version, `NEEDS_VERSION_CHANGED` blocks until `POST …/msel/acknowledge-needs-version` (which reopens the MSEL like an edit).
- Without ORM relationships the service flushes level by level (MSEL → actors/phases → injects → actions).
- **Validator stamp**: `_stamp_validation` in `save_msel` — marking an inject validated records the *saving* user (`validated_by_id` + the name then in `validated_by`); a stored validation is kept while the payload's `validated_by_id` is unchanged, and any other id (client's own, an override, a forged one) makes the saving user the validator; back to draft clears it; a deleted account's validations read "Deleted user".
- Library single-row writes (both count as MSEL edits and are in `DESIGN_ENDPOINTS`): `POST /ttx/{ttx_id}/msel/injects` (copy from a library → `{msel, conversion}`), `DELETE …/msel/injects/{inject_id}`, `POST …/msel/threat-actors`, `DELETE …/msel/threat-actors/{id}`.
- **EEG**: `EEGObjective.expected_actions` — Evaluators from the latest READY snapshot, Planners' preview from the live MSEL (`EEGRead.msel_version`). `TTXRead.msel_status` is `None` until first opened.
- Cascade: `delete_msels_for_ttx` runs before `delete_forms_for_ttx` (phases and injects reference objectives).

### Validation report (rules M01–M21)
`ValidationReport` reused, `section` = MSEL tab: 1 scenario, 2 phases, 3 injects (incl. branches and bursts), 4 threat actors, 5 coverage, 6 review (`REVIEW`: recipient load, `NEEDS_VERSION_CHANGED`). `ready` blocks draft → in_review, `approved` additionally blocks → ready, `warnings` never block.
- M07 only requires a mandatory inject per phase. Contingent injects are optional (the facilitator's plan B) and never warned about. M11 is retired.
- M12 `INJECT_NOT_VALIDATED` — mandatory injects must be validated for READY.
- M24 `ACTION_WITHOUT_OBJECTIVE` (warning) — an action of an inject of the `inject` format evidences none of its objectives, so no EEG lists it (fine for context the Controller needs). M04's action count per objective counts only the actions that evidence it.
- M13 `VAGUE_EXPECTED_ACTION` (warning) — an internal verb an evaluator can't see (`VAGUE_ACTION_WORDS`: manage, assess, check, analyse the situation; gestionar, valorar, comprobar, analizar la situación); the frontend mirrors the list and quotes the words in the message (`vagueActionWords`).
- M22 `CHECK_AFTER_PHASE_END` (blocking) — a contingent inject's check minute past its phase's length. M23 `ACTION_PAST_PHASE_END` (warning) — delivered at (mandatory T+, or phase start + check minute) + an action's "within" past the phase end; one-click fix `actionsToPhaseEnd` (`issueFixes`, `deliveredAt` mirrors the backend's `_delivered_at`).
- M06 warns `SESSION_START_UNCOVERED`/`SESSION_END_UNCOVERED` past 10 min of session no phase holds; `PHASE_GAP` warns on any gap between phases; overlaps and `INJECT_OUTSIDE_PHASE` are warnings with one-click fixes.
- Branches: M14 `BRANCH_NOT_ANCHORED` (blocking), M15 `BRANCH_CYCLE` (blocking), `BRANCH_FROM_OTHER_PHASE` (blocking), M16 `BRANCH_WITHOUT_REJOIN` (warning), M17 `BRANCH_REJOIN_INVALID` (blocking).
- ATT&CK: M18 `ATTRIBUTION_WITHOUT_TECHNIQUE` (threat-actor attribution only), M19 `ATTRIBUTION_WITHOUT_ACTOR`, M20 `TECHNIQUE_OFF_ACTOR_PROFILE`, M21 `THREAT_ACTOR_WITHOUT_INJECTS` — all warnings. A nameless threat actor is `MSEL_INCOMPLETE`.
- `RECIPIENT_OVERLOAD` (section 6).
- Rooms (`docs/features/rooms.md`, only when the exercise uses rooms): M25 `ROOMS_MISSING` (blocking) — played in rooms with none defined; M26 `ROOM_WITHOUT_INJECTS` (warning, shown in Injects with the room filter) — no inject is played in a room (an all-rooms inject counts for every room). An inject's `room_ids` naming a room not on the exercise is 422 `UNKNOWN_ROOM` on save.

### Storyline branches (contingent injects)
- A contingent inject records `branch_from_id` (the inject it hangs from), `branch_action_id` (an expected action of that inject whose absence fires it; `fk_inject_branch_action_id` is `use_alter`, it closes a cycle with `inject_expected_action`) and `rejoin_inject_id` (the mandatory inject where the storyline resumes).
- The payload names them by key or id (`branch_from_key`/`branch_action_key`/`rejoin_key`; expected actions carry a `key`). `MselSaveRequest` **drops** an end that no longer points inside the MSEL (removed inject, itself, another inject's action) and clears them on mandatory injects — never 422, so removing an inject never blocks autosave. The save clears every branch first and rewrites them once all rows exist; `remove_exercise_inject` and `delete_msels_for_ttx` cut them before deleting.
- Rules: it must branch off an inject (mandatory or contingent) **of its own phase**; several may hang from one, and branches may hang from branches; where it comes back is optional, but if set it's a mandatory inject **later** than the fork (any phase).
- Frontend mirrors: `branchForkTime`/`branchesFrom`/`validRejoin` (`lib/msel.ts`). The wizard's "Branches off" lists only its phase's injects (required; a phase change clears a branch point now elsewhere) and "Back to the storyline at" only valid later mandatory injects; step issues `branchFrom`/`branchOtherPhase`/`rejoinInvalid`; fixes "Move it to <phase>, the phase it branches off" and "Clear where it comes back". `reconcileSaved` maps the response's branch ids back to keys.

### Inject images
- `MselImage` (per MSEL: random `stored_name` under `settings.MSEL_IMAGE_UPLOAD_DIR`, never `StaticFiles`) + `InjectImage` (inject, image, position, caption). `services/msel_image_service.py`: upload accepted by extension + leading bytes, then decoded and re-encoded by `image_processing.process_attachment_image` (EXIF/metadata and appended bytes dropped, longer side ≤ `MSEL_IMAGE_MAX_DIMENSION_PX`, PNG stays PNG, the rest JPEG); ≤ 5 MB, ≤ 60 per MSEL, ≤ 10 per inject. Served inline only through `GET …/msel/images/{id}` (Planner), `private, no-store`, `nosniff`.
- The save links them (`InjectInput.images`, `UNKNOWN_IMAGE` 422 for an image of another MSEL) and then drops images no inject links, no `MselSnapshot` shows and older than a day (`drop_unused_images`; files unlinked after commit). `delete_msels_for_ttx` removes all.
- Wizard step 1, under the inject text (a `FormattedTextArea`): `InjectImagesField` — upload, thumbnail, caption, move up/down, remove. The inject cards PDF draws each image under its card (scaled to the column, ≤ 90 mm high) with its caption.

### Inject files
- Evidence the players download and analyse (logs, packet captures, memory dumps, exports…). `MselFile` (per MSEL: random `stored_name` with no extension under `settings.MSEL_FILE_UPLOAD_DIR`, `original_name`, `size_bytes`, `sha256`; never `StaticFiles`) + `InjectFile` (inject, file, position, description). `services/msel_file_service.py`: **any type**, stored byte for byte (it's evidence: nothing is re-encoded, parsed or executed), streamed to disk while hashing; ≤ `MSEL_FILE_MAX_BYTES` (50 MB, 413 `MSEL_FILE_TOO_LARGE`), not empty (`MSEL_FILE_EMPTY`), ≤ `MSEL_FILE_MAX_PER_MSEL` (60, `MSEL_FILE_LIMIT`), ≤ 10 per inject. The name is sanitized (`safe_filename`: no directories or control characters, ≤ 255).
- Served only as an opaque download (`download_headers`): `application/octet-stream`, `Content-Disposition: attachment; filename*=UTF-8''…`, `nosniff`, `private, no-store`, under the API's deny-all CSP — never inline, so a browser never renders an uploaded HTML or SVG. `GET …/msel/files/{id}` (Planner) and, in the session, `GET …/run/files/{id}`.
- Same life cycle as images: the save links them (`InjectInput.files`, `UNKNOWN_FILE` 422), `drop_unused_files` drops what no inject links, no snapshot shows and is older than a day; `delete_msels_for_ttx` removes all. The platform doesn't scan them: Planners hand out defanged samples (the field's hint says so).
- Wizard step 1, under the images: `InjectFilesField` — upload (no `accept` filter), download link, size, SHA-256 (`common/FileDigest`, copy button), description, move up/down, remove. The inject cards PDF lists each file (name · size · first 16 hex of the SHA-256, then its description) in a "Files" row; the content is never drawn.
- **Preview of text files**: a file whose name says it's text (`lib/textPreview.ts`'s `isTextPreviewable`: logs, CSV/JSON/XML/YAML exports, configs, scripts, emails…) gets **Preview** next to its download, in the wizard and in the Playground (`common/TextFilePreview`). `GET …/msel/files/{id}/preview` (Planner) and `GET …/run/files/{id}/preview` (same rule as the download) return its first `PREVIEW_MAX_BYTES` (256 KiB) decoded on the server (`msel_file_service.text_preview`: UTF-8, or UTF-16 with its byte-order mark; a NUL byte otherwise means binary → 409 `MSEL_FILE_NOT_TEXT`; CRLF folded, control characters but tab/newline replaced by U+FFFD, never a split multi-byte character) as JSON (`MselFilePreviewRead`: text, `truncated`, `encoding`, `limit_bytes`). The page shows it in a `<pre>` as plain text (wrap toggle, line count, "showing the first …" when truncated): the file itself is still never served inline.
- **Size limit and raising it.** 50 MB per file by default, set with `MSEL_FILE_MAX_BYTES` (bytes) in `.env`; `MSEL_FILE_MAX_PER_MSEL` caps the count. Raising it also lets a scenario file carry bigger files (`ScenarioFile.data` follows it), so check `SCENARIO_MAX_BYTES` (200 MB) still fits what an exercise holds. The UI copy states the default (`creator.msel.files.hint`, `creator.msel.files.errors.tooLarge` in both `en.json` and `es.json`): change it with the limit.
- **Reverse proxy.** Whatever sits in front of the backend (Nginx, a load balancer, a WAF) has its own request-size cap, usually far below 50 MB (Nginx `client_max_body_size` defaults to 1 MB), and refuses a bigger upload before the backend sees it: the Planner gets a generic upload error instead of `MSEL_FILE_TOO_LARGE`. Set it to at least `MSEL_FILE_MAX_BYTES` plus a margin for the multipart envelope on `/api/v1/ttx/*/msel/files`, and to at least `SCENARIO_MAX_BYTES` on the scenario import routes; raise the proxy's body and read timeouts too (`client_body_timeout`, `proxy_read_timeout`, `proxy_send_timeout`), since a large file on a slow link takes a while. Every time the limit goes up, the proxy goes up with it.
- **Antivirus.** TTX-Zone does not scan inject files: they're stored and served byte for byte, never opened, and only ever downloaded as `application/octet-stream` attachments. In a cyber exercise a file may legitimately hold a malware sample or indicators that a scanner flags, so scanning is the operator's choice, outside the app:
  - on the host, a scanner (e.g. ClamAV) over `backend/uploads/msel-files/`: a file it quarantines or deletes goes missing and its download answers 404 `MSEL_FILE_NOT_FOUND` (the inject still lists it, as with a lost image) — prefer reporting over deleting;
  - at the proxy or WAF (ICAP or similar) on the upload route, which refuses the upload before it's stored;
  - the players' own endpoint protection, which sees each download.
  Whatever the setup, Planners should hand out defanged samples, and live malware only inside a password-protected archive (the usual `infected` convention); the field's hint says so in the UI.

### Rendered artifacts
An inject's content can be shown to the table as a **simulated artifact** instead of plain text: an email, a press release, a social media post or a chat message.
- `Inject.artifact` (JSONB, nullable; migration `45ebf79e74d1`) holds `InjectArtifact` (`schemas/ttx_msel.py`, `extra="forbid"`): `kind` (`ArtifactKind`: `email`, `press_release`, `social_post`, `chat_message`) and the template's header fields, all plain text — `sender`, `sender_address`, `recipient`, `subject`, `timestamp` (≤ 64, free text such as "Day 1, 08:12"), `location`. Their meaning follows the kind (an email's subject is a press release's headline; `location` is a press release's dateline or a chat's channel). The body is always the inject's own `content`.
- On `InjectInput`/`InjectRead` (defaults to null, so older snapshots load), frozen in the READY snapshot, served to the table in `RunInjectRead.artifact`, carried by scenario files (format version 5).
- Wizard step 1, under the content: **Shown to the table as** (`creator/msel/InjectArtifactField`): Plain text or a kind; picking one prefills the sender with the inject's simulated actor (`lib/artifacts.ts`'s `newArtifact`, keeping what was typed); the kind's fields (`KIND_FIELDS`) and a **Preview**.
- PDFs: the full MSEL (in the inject's cell), the Controller guide and the inject cards print a **Shown as** row with the kind and the fields filled in (`msel_pdf_service._artifact_markup`, its `_ARTIFACT_FIELDS` the twin of the wizard's `KIND_FIELDS`; labels `artifact_kinds`/`artifact_fields` in `msel_pdf_labels.py`).
- Playground stage: `common/InjectArtifactView` draws the template — never the author's text as markup (the body goes through `FormattedText`), a neutral initial instead of an avatar (colour marks state only), and a **Simulated** mark on every artifact so a screenshot can't pass for the real thing.

### PDF exports
- `GET /ttx/{ttx_id}/msel/export/msel.pdf?lang=` (`services/msel_pdf_service.py`, copy in `msel_pdf_labels.py`, tests `test_msel_pdf.py`): the full MSEL for the planning team (everything + coverage). Any other `kind` is 422.
- Its storyline map sits on a page of its own turned landscape, after Scenario and threat actors (`build_pdf(..., landscape_pages=True)`: portrait/landscape `PageTemplate`s, `NumberedCanvas` decorates each page at its own size). `services/storyline_pdf.py`: `storyline_layout` mirrors `lib/storylineMap.ts` (change both together; `test_storyline_layout.py`), `StorylineFlowable` draws it in the app's light colours — phase boxes, accent storyline and stops (labels in rows that climb only to avoid overlapping, leader lines under them), purple branches with labels above their lane (dashed without a way back), time jumps, T+ and scenario-time axis (ticks spaced by label width), legend. Session documents stay portrait without it.
- The session documents built from the MSEL -- Facilitator and Controller guide, SitMan, inject cards, EEG -- are exported from Creator -> Session plan (`docs/features/conduct-prep.md`); their stories (`_facilitator_story`, `_sitman_story`, `_cards_story`) and export schemas stay in `msel_pdf_service.py`.
- A READY MSEL exports from its snapshot; a live one only without errors (409 `MSEL_INCOMPLETE`) and with a "Not final" notice. Logo, TLP top and bottom and an "EXERCISE – EXERCISE – EXERCISE" band on every page. `{code}_{kind}_v{version}_{TLP}.pdf`, `attachment` + `no-store`. Session length prints as a span ("3 h"); the MSEL and facilitator guide print time jumps and the Scenario start (not the SitMan).
- **Content safety is structural**: SitMan and inject cards are built from their own export schemas (`SitmanExport`, `InjectCardsExport`) with no field for expected actions, facilitator notes or triggers; the tests search the PDF text for them. The stop keyword is on the SitMan (every participant must know how to halt), never on the cards. Neither shows threat actors or attribution.
- Frontend: `MselDownloads` is a single "Download PDF" link (disabled with a reason while dirty or with errors) and a link to the Session plan's documents step.

## Frontend
`components/creator/msel/`, `lib/msel.ts`, `hooks/useMselIssueMessage.ts`; tests `CreatorMselSection.test.tsx`. Section `msel` (`/creator/:ttxId/msel`, third in `CREATOR_SECTIONS`, behind `CreatorDesignGate`). The old Storylines / Timeline / Questions sections are gone: their URLs (`/creator/:ttxId/{storylines,timeline,questions}`) redirect via literal routes to `?tab=scenario|injects|phases`.

### Page model (shared with the needs analysis)
- Tabs in `?tab=` (`MSEL_TABS`, in order: scenario 1, threats 4, phases 2, injects 3, coverage 5, review 6 — the number is the report section; `?tab=load` → Review).
- One page-level `MselDraft` (`draftFromMsel`/`payloadFromDraft`/`reconcileSaved`/`adoptSavedIds`; rows carry a `key`, injects point at phases/actors by key), autosaved through `hooks/useAutosavedDocument` (blocking code `UNKNOWN_OBJECTIVE`). The live report drives tab counts, `SectionIssueList`, `IssueSummary` and red fields. Confirm on the first edit past draft; read-only banner when `editable: false`.
- The header's Downloads menu (`MselDownloads`, a `<details>` disclosure) is disabled while there are unsaved changes or errors. `?inject=<id>` opens that inject once (the page drops the param).
- **Issue boxes** (`SectionIssueList`, shared): issues about one row are grouped under its name with a count ("PH-15 | Detection (2)") via `lib/issueGroups.ts` (`groupIssues`/`withoutItem`); red = blocks the next step, amber = worth reviewing. The tab list shows a warnings-only tab as an amber ✓ and a red count only for blockers; Review shows a green ✓ once Ready.
- **A warning shows only where something can be done about it**: `relocateIssues` moves the ones fixed by writing injects (unused threat actor, phase without a mandatory inject, recipient overload) to Injects; picking one opens Injects filtered on it (`issueInjectFilter`).
- **Timing fixes are one click, never automatic**: `issueFixes` (`lib/msel.ts`, `fixes` prop) — overlap: start the phase when the previous ends (later phases move too) / end the previous when it starts; gap: turn it into scenario time / extend the previous; uncovered start/end: start at T+0, extend the last phase / shorten the session; `INJECT_OUTSIDE_PHASE`: move it inside its phase / into the phase holding its time. Applied to the draft with an Undo toast. Phase warnings state where and by how much (`useMselIssueMessage` adds the times and the previous phase).

### Tabs
- **Scenario**: general parameters and duration only. **Summary for Players** is formatted text (`common/FormattedTextArea`, the same Markdown subset as the exercise description, ≤ 5 000 chars), printed in the MSEL and SitMan PDFs through `pdf_common.formatted` (mirrors `FormattedText`'s parser: **bold**/_italic_ as `<b>`/`<i>` on the registered Vera family, "•"/"1." lists, blank-line paragraphs; escaped piece by piece, so typed markup prints as typed). Session length in hours (`HoursInput`: "3", "2,5", "2.5"; stored as minutes) with the needs form's maximum as hint; time compression as a preset select ("Each minute of session represents" 1 min / 10 min / 30 min / 1 h / 4 h / 1 day, `COMPRESSION_PRESETS`; a saved non-preset value stays selectable); a Session → Scenario summary. A new MSEL starts at 180 min (capped by the needs form) and 60 (`DEFAULT_SESSION_MINUTES`/`DEFAULT_TIME_COMPRESSION`).
- **Threat actors** (`ThreatActorsTab`, section 4): `ThreatActorsSection` + the pinned release with its upgrade banner (`AttackRelease`). Detail in `docs/architecture/attack.md`. Optional (its copy says so; an MSEL with no threat actors is complete). Migration `d7a4e9b1c062` trimmed older untouched MITRE copies (in draft MSELs) to the techniques their injects use.
- **Phases**: table + `RowDialog`. 2–8 phases (the minimum of 2 is a TTX-Zone design rule so the scenario can evolve across time jumps). ### Inject wizard (`InjectDialog.tsx`, Modal `xl`, `align="top"`)
Shared by Injects, Coverage and the storyline map (exported; opens on whatever tab is open).
- A new inject opens on **What do you want to add?** (`InjectFormatChooser`): three cards, Inject, Discussion, Poll, from every entry point (list, map, branch, Coverage). The format sets the steps (`injectSteps`): inject and discussion go through the five below, a poll through Context, Question and options, Review. An existing inject shows the format as `RadioCards` at the top of Context; changing it drops what only the old format uses.
- Left rail of steps; below `md:` a "Step 2 of 5" select; a context card (type, phase, time) under the rail; Back / "Next: <step>", Close on the last step, × in the header. Anchored to the top over a minimum height so switching step only grows it downwards.
  1. **Context** — type as `common/RadioCards` (Mandatory / Contingent, one-line hints); phase, title, text; time asked **relative to its phase** ("Session time (minutes after the phase starts)", hint "T+01:05 in the session · +3 d 6 h in the scenario"), stored as session minutes — changing phase keeps the minutes into the phase. A new mandatory inject is proposed a time by `nextOffsetIn`: as the phase opens if first, else 5 min after the phase's last (`NEXT_INJECT_GAP_MINUTES`), stacked at the phase end when out of room. Contingent: trigger / purpose / Branches off / Fires if not observed / Back to the storyline at / Checked at (optional, minutes after the phase starts).
  2. **Source and audience** — source (+ New actor / Add from the library via `ActorLibraryPicker`, never adding a sender twice), delivery method (picking an actor prefills its `channel`), recipients as toggle chips (the needs analysis' participating areas and third parties), attachments.
  3. **Evaluation** (a discussion inject's is **Discussion points**: no objectives, the rows are what the table talks about) — objectives as toggle chips (`CODE | title`), expected actions as compact rows (description, responsible area, within) — with ≥ 2 objectives, an "Evidences" row of small toggles under each action (`ActionObjectives`; an objective added to the inject is ticked on every action, one removed leaves them all).
  4. **Whose activity** — three radio cards: A threat actor (its ATT&CK techniques expected, M18), Noise (another attack, commodity malware, false positive — techniques optional), Not an attack (regulator, press, business decision — no ATT&CK, stored as no attribution). Technique picker and "Add to the scenario's techniques": see `docs/architecture/attack.md`.
  5. **Review** — recap of steps 1–4 with Edit links, facilitator notes and a **Validated** switch, disabled (naming the steps left) until Context, Source and audience and Evaluation are complete; shows "Validated by …" and offers "Override validation" when it was someone else.
- Rail marks from `injectSectionStatus` (● current, ✓ complete, ! to complete — only once visited, or always for an existing inject — amber ● worth reviewing, ○ not started/optional), one accessible name per button ("2 Source and audience (complete)"). Each step states why it isn't complete at its top (`injectSectionIssues`, from which the status derives).

## Copy and display rules
- **Time terminology**: only **session** (the real meeting: start, length, T+) and **scenario** (the simulated story: "scenario time", "Scenario start", "later in the scenario"). Never "meeting" or "simulated incident" for these. Code keeps the `incident_*` names. `formatOffset` renders `T+hh:mm`. A jump shows on its phase band, in the Phases table ("2 d later in the incident") and the Scenario tab's total.
- **Coded rows are never a bare code and never comma-listed** (needs, objectives, phases, injects, threat actors, expected actions, ATT&CK techniques; app and PDFs; `lib/codeRef.ts`, `common/CodeRef.tsx`, `pdf_common.code_ref`/`code_ref_cell`/`ref_lines`):
  - **table cell** = `CodeRef variant="stacked"`: the code as label (body font, primary colour), the title muted and smaller under it, cut by the cell (full title on hover). A table merges its Code and Name/Title columns into that cell.
  - **one line** (lists, `CheckboxGroup`'s `code`, sentences) = inline `CODE | Title…` (bar hidden from screen readers, titles cut at 40 characters).
  - **plain text** (native `<option>`, toasts, aria-labels, dialog titles, validation messages, fix labels) = `codeRefText(code, title, pending)`, rendered through `CodeText` (keeps every `CODE_PATTERN` match out of translation).
  - **several** = `CodeRefList`: one per line, "+N more" past 4, "Show less".
- Glossary includes MSEL, SitMan, ATT&CK, TTP. `EegView` lists each objective's expected actions.
