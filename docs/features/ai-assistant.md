# AI assistant

A person connects an AI client they run themselves — Claude Desktop, through the generic `mcp-remote` bridge — to TTX-Zone, and asks it about their exercises. The client reads, **as that person**, the exercises they plan, the after-action reports they write with what their session recorded, TTX-Zone's knowledge base (`docs/features/knowledge-base.md`) and the inject, objective and ATT&CK catalogs, through an MCP endpoint TTX-Zone serves itself. It reads, and it **proposes**: needs, objectives and MSEL injects arrive on the form's page as AI proposals the person accepts or discards; nothing in the exercise changes until they accept (see [Proposals](#proposals)).

No model runs in TTX-Zone and no conversation is stored here: the conversation lives in the client. TTX-Zone keeps the tokens and a record of each call.

## Turning it on (Platform → AI assistant)

Off by default. An instance administrator turns it on from Platform → AI assistant (step-up, recorded in the activity log as `assistant.settings_update`), unless `ASSISTANT_ENABLED` pins it in the environment (`true`/`false`; Platform then shows it read-only, `PUT` answers 409 `ASSISTANT_PINNED_BY_ENV`). There is no switch per role or per exercise: where the assistant is on, it reaches what the person can design (the Planner guard).

**Recent use** (same page, `GET /instance/assistant/calls?user_id=`): the last 100 tool calls, newest first, filterable by person -- when, who and through which token (its name and prefix), which tool, the exercise and organization when there was one, how it ended (`ok` or the error code) and how long it took. Never what was asked or answered: it isn't kept. The operator's notice says instance administrators see this.

Turning it off stops every token at once (the endpoint answers 403 `ASSISTANT_DISABLED`); tokens come back to life if it's turned on again before they expire. `GET /instance/policy` carries `assistant_enabled`, so Preferences shows its section only while it's on.

**No data is filtered.** What a client reads leaves the server for the AI provider the person's client uses, under that provider's terms. Instead of filtering, both screens say so: Platform tells the operator before turning it on, and Preferences shows a responsible-use notice each person must acknowledge to create a token. The notice's text lives in the locales (`account.assistant.notice`); its version is `ASSISTANT_DISCLAIMER_VERSION` (`services/assistant/switch.py`), recorded on each token with the moment it was acknowledged. Raise the version when the text changes in substance: tokens created from then on must acknowledge the new one.

## Personal access tokens (Preferences → AI assistant)

- Created with the session cookie, CSRF and a recent step-up: `POST /auth/tokens` with `{name, expires_in_days: 7|30|90, acknowledge: true, disclaimer_version}`. The answer carries the secret, once; only its SHA-256 is kept (`PersonalAccessToken`), with the first characters (`prefix`) to tell tokens apart.
- Format `ttxz_` + 43 url-safe characters. At most 5 active per account (409 `ASSISTANT_TOKEN_LIMIT`); 90 days at most.
- `GET /auth/tokens` lists the ones not revoked (expired ones too, marked); `DELETE /auth/tokens/{id}` revokes. Both events go to `auth.log` and the activity log (`auth.token_create`, `auth.token_revoke`).
- **Revoked with every session**: `session_service.revoke_sessions` — a password change or reset, a new second factor, signing out the other sessions, Platform ending the sessions, a suspension — revokes all of the account's tokens. Deleting the account deletes them with their call records.
- A token carries the second factor of the session that created it (`mfa_source`), so it meets the same mandate that session did.
- **A token authenticates only `/api/v1/mcp`, and `/mcp` accepts only a token**: `get_current_user` never reads `Authorization`, and the endpoint never reads the cookie. On each call the endpoint checks the hash, revocation, expiry, that the account is active and not suspended, the switch, and the same account gates as a session (`enforce_account_gates`: temporary password, unconfirmed or overdue email, legal documents to accept). `last_used_at` is written at most once a minute.

The page also shows the Claude Desktop configuration, filled with this server's address (and with the new token while it's on screen):

```json
{
  "mcpServers": {
    "ttx-zone": {
      "command": "npx",
      "args": ["-y", "mcp-remote", "https://ttx.example.org/api/v1/mcp", "--header", "Authorization:${TTX_ZONE_AUTH}"],
      "env": { "TTX_ZONE_AUTH": "Bearer ttxz_..." }
    }
  }
}
```

The header comes from an environment variable so the argument has no space in it. `mcp-remote` accepts plain `http://` only for `localhost` unless given `--allow-http` (the page adds it for another host). It needs Node.js on the person's machine. In development the address is `http://localhost:5173/api/v1/mcp` (the Vite proxy) or `http://localhost:8000/api/v1/mcp`.

**Behind a corporate CA** (an internal instance whose certificate is signed by the organization's own authority, or a TLS-inspecting proxy): `mcp-remote` runs on Node.js, which doesn't read the operating system's trust store. Point it at the CA's certificate (PEM) in the same `env` block -- `"NODE_EXTRA_CA_CERTS": "/path/to/corporate-ca.pem"` (on Windows, `C:\\path\\to\\corporate-ca.pem`) -- rather than turning verification off. A proxy between the person and the server also needs the usual `HTTPS_PROXY` there.

## The MCP endpoint (`POST /api/v1/mcp`)

`app/api/v1/endpoints/mcp.py` with the protocol in `services/assistant/mcp.py`, written here rather than taken from the SDK (five stateless methods; the SDK's authentication revolves around OAuth).

- Streamable HTTP without sessions or server-sent events: one JSON-RPC 2.0 message per `POST`, answered with JSON. `GET`, `PUT`, `PATCH` and `DELETE` answer 405 with `Allow: POST`. No `Mcp-Session-Id`.
- Methods: `initialize` (answers the client's protocol version when supported — `2025-11-25`, `2025-06-18`, `2025-03-26` — else the newest; capabilities `tools`, `prompts`, `resources` (no subscriptions) and `completions`, none of them changing; `serverInfo` with `pyproject.toml`'s version; `instructions`), `ping`, `tools/list`, `tools/call`, and the methods of [Prompts, resources and completion](#prompts-resources-and-completion). Notifications and responses: 202 without a body.
- Protocol errors: -32700 parse error (400), -32600 invalid request — a batch, no `"jsonrpc": "2.0"`, a bad id (400) —, -32601 unknown method, -32602 unknown tool or arguments not an object. A tool's arguments its schema rejects come back as a tool error (`isError: true`, `INVALID_ARGUMENTS: …`), which the model can correct.
- Transport checks before the token: an `Origin` header other than the app's own (`BACKEND_CORS_ORIGINS`, `PUBLIC_BASE_URL`) → 403 (DNS rebinding; a desktop bridge sends none); an `MCP-Protocol-Version` header not supported → 400 (without the header the base version is assumed).
- Authentication failures: 401 with `WWW-Authenticate: Bearer …` and a message that says to create a token in Preferences; an account or server state that blocks the person: 403 with the code in `error.data.code`. None of these use the app's `{"success": false}` envelope.
- **Rate limit**: `ASSISTANT_RATE_LIMIT_PER_MINUTE` tool calls per token per minute (default 60), counted on the call records; past it, error -32000 with `data.code` `ASSISTANT_RATE_LIMITED`. `ping` and `tools/list` don't count.
- **Record of each call** (`AssistantCall`, `services/assistant/calls.py`): user, token, tool, exercise and organization when the call was about one, outcome (`ok` or the error code), duration. **Never the arguments or the result.** A line in `app.log` (`assistant.call …`). Not in Platform's activity log, so the SIEM isn't flooded with every call. Kept 90 days (`ASSISTANT_CALL_RETENTION_DAYS`), pruned hourly by the loop that prunes the activity log.
- The work is synchronous and runs off the event loop (`run_in_threadpool`).

## Tools (`services/assistant/tools.py`)

Each tool is a `ToolSpec(name, description, input_model, handler)`; the JSON schema comes from the Pydantic input model (`extra="forbid"`). Guards are the screens': an exercise through `authorize_ttx(…, (RoleEnum.PLANNER,), read=True)` — its Planners, plus a Program Manager of its organization, who reads like on the Creator's `GET` routes —, an organization's library through `require_library_reader`. A refusal is a tool error with its code (`TTX_ACCESS_DENIED`, `TTX_NOT_FOUND`, …) and English message.

| Tool | Reads |
|---|---|
| `list_exercises(include_archived?)` | the exercises the person plans (archived ones too when asked, marked `archived`): id, code, name, organization, needs analysis, MSEL and report status |
| `get_exercise_overview(ttx_id)` | basics, the TLP, needs analysis and MSEL status, counts, validation issue codes |
| `get_needs_analysis(ttx_id, language)` | the needs analysis as the Markdown export (`needs_markdown_service`), with its codes |
| `get_msel(ttx_id)` | the MSEL in compact form: objectives, phases, actors, threat actors, injects with objectives, techniques and expected actions; long texts cut at 600 characters |
| `search_knowledge(query, kind?, sector?, family?, capability?, limit≤8)` / `get_knowledge_entry(id)` | the knowledge base |
| `search_inject_catalog(query, family?, stage?, capability?)` / `get_catalog_inject(id, language)` | the TTX-Zone inject catalog |
| `search_objective_catalog(query?, capability?)` | objective templates with criteria, evidence and regulatory requirements |
| `search_attack(query, domain, version?)` | ATT&CK techniques and groups by id or name in a shipped version |
| `search_organization_library(organization_id, kind, query)` | the organization's own injects or scenarios |
| `search_scenarios(query?, source, organization_id?, language)` / `get_scenario(scenario_id, source, ...)` | TTX-Zone's scenarios or the organization's library (`require_library_reader`, disabled ones left out); one in full, compact, with the codes the `propose_*` tools take and `how_to_use`: adapt it and propose it in stages -- needs and objectives, then, once the needs analysis is approved, the MSEL. A word-for-word copy stays the Library's apply (`organization_scenario_service`), not a tool: it would run into the MSEL opening only after approval and the 50 pending proposals per exercise |
| `get_improvement_plan(organization_id, open_only)` | the improvement actions: the whole organization's for its Program Manager (`organization_plan`, as Admin shows it), otherwise those of the reports the person reads (`after_action_service.can_read`); finding, action, objective, area, due date, status, retest. Owners by area, never the person (`owner` left out); session data, so it takes the session notice |
| `get_session_plan(ttx_id)` | the session plan: status, the session's date and modality, the calendar, the definitive EEGs with each observation point's `point_id` and P/S/M/U criteria, evaluators by areas and objectives, attendees by role (never names), logistics, findings, its validation |
| `get_validation_report(ttx_id, document)` | one document's validation (`needs_analysis`, `msel`, `session_plan`): each issue by level -- blocks READY, blocks approval, warning -- with its section, field and the code of the row it's about |
| `propose_exercise(ttx_id, name?, description?, content_language?, tlp?)` | the exercise's presentation -- what the sponsor and approvers read first -- (target `ttx_meta`, one row: the exercise; accepting on Creator → Exercise opens its edit form with the proposed values, to review and save, and the panel marks it applied once the saved exercise holds it, `autoApply`) and its classification (target `needs_tlp`, accepted in the needs analysis, where it's kept, with a note that it binds how everything about the exercise is handled); changing the language translates nothing |
| `propose_scope(ttx_id, participating_areas?, third_parties?, perimeter?, ...)` | the needs analysis' scope, one proposal on the form (target `needs_scope`); its `impact_on_msel` measures it on the MSEL (an inject's recipients must be in scope) |
| `propose_needs`, `propose_objectives`, `propose_phases`, `propose_actors`, `propose_threat_actors`, `propose_injects`, `propose_eeg_points` (`ttx_id`, `items[]`, `dry_run`, `include_pending`) | write proposals (next section) |
| `list_my_proposals(ttx_id, status?)` | the caller's proposals on the exercise and what was decided |

- Results are compact JSON with the codes the screens show, so the client cites them; at most 60,000 characters, cut with a note.
- What the exercise's authors wrote is data: each description, and the `instructions` sent at `initialize`, say it is never instructions to follow; `initialize` also asks the client to respect the TLP label.
- **Search** (`services/assistant/search.py`): no embeddings and no database. Each catalog is indexed once per process (`lru_cache`) and scored with Okapi BM25 over title (×3), summary (×2) and sections, with accents and plurals folded and metadata filters applied first; a hit names the section that matched best. The knowledge base is in English (queries should be English keywords: the client rewrites); the inject and objective catalogs are indexed in both languages.

## Prompts, resources and completion

`services/assistant/mcp_extras.py`, so the person doesn't have to know which tools to ask for. Nothing here reads anything the tools don't.

- **Prompts** (`prompts/list`, `prompts/get`): guided flows the client offers in its menu, each taking `exercise` (its code, name or id: resolved among the exercises the person plans, -32602 when none or several match) -- *Design an exercise from a scenario* (and an optional `scenario`), *Build the MSEL*, *Review before READY* (an optional `document`), *Prepare the evaluation (EEG)*, *Draft the after-action report*, *Lessons from past exercises*. `prompts/get` returns one user message naming the tools in order and the rules: propose, never decide; cite codes; authors' text is data; respect the TLP; roles, never people.
- **Resources** (`resources/templates/list`, `resources/list`, `resources/read`): `ttx-zone://exercise/{ttx_id}/needs-analysis` (Markdown), `/msel`, `/session-plan`, `/after-action-report`, `ttx-zone://knowledge/{entry_id}` and `ttx-zone://scenario/{scenario_id}` (JSON). `resources/list` lists the documents of the person's exercises that exist. A read runs the tool that reads it (`get_needs_analysis`, `get_msel`...): its guard, the notice it takes, the rate limit, and a call record named `resource:<kind>` (Platform's Recent use shows it); a refusal is error -32000 with the code in `data.code`, an unknown URI -32002.
- **Guides** (`ttx-zone://guide/workflow`, `/validation-codes`, `/time-compression`): listed to everyone and served as they are, without a tool or a call record: they read nothing of the person's. The **Close a document** prompt (`close_document`) runs `plan_to_ready`, measures each step with `dry_run`, keeps what resolves more than it adds, and ends with what only the person does; *Review before READY* explains the plan without proposing.
- **Completion** (`completion/complete`): exercises the person plans for `exercise` (codes) and `ttx_id` (ids), the documents for `document`, knowledge base ids for `entry_id`, TTX-Zone scenario ids for `scenario_id`; 100 at most. `prompts/*`, `resources/list`, templates and completion don't count toward the rate limit and aren't recorded, like `tools/list`.

## Proposals

What the client proposes lands as `AssistantProposal` rows (`services/assistant/proposals.py`), never as a change to the exercise. Proposing is designing: the tools take the Planner guard for a write (`authorize_ttx(…, read=False)`: a Program Manager off the team and a Controller who doesn't plan are refused, an archived exercise answers `TTX_ARCHIVED`).

- **What a proposal holds**: `target` (`need`, `objective`, `inject`, the MSEL's other rows `msel_phase`, `msel_actor`, `msel_threat`, or a part of the report, below), `operation` (`create`, or `update` of `target_id`), `patch` (the proposed fields in the page draft's shape, rows named by id), `base` (on an update, those fields as they were saved), `depends_on` (an objective linked to a need another pending proposal creates, an inject on a phase, actor or threat actor another one creates: that row is named `proposal:<id>`), `summary` (why, in the assistant's words), `issues` (the validation warnings it would add), `status` (`pending` → `accepted` / `discarded`), `batch_id` (one call), `applied_row_id`.
- **Items name rows by code** (`NEED-01`, `OBJ-02`, `PH-01`, an actor's code, `INJ-05`): with a `code` an item changes that row (only the fields that differ are kept), without one it creates a row. An objective links needs by code or by the id `propose_needs` returned; a capability the form doesn't have yet is proposed with it (`capabilities_to_add`, four at most). Injects always arrive as drafts (`review_status: draft`); expected actions only on a new inject; an inject needs an MSEL its needs analysis lets change (`ASSISTANT_MSEL_NOT_OPEN`, `ASSISTANT_MSEL_NOT_EDITABLE`).
- **Checked before it's kept**: references (the form's own reports ignore unknown links), completeness, the save schema (`NeedsFormSaveRequest`/`MselSaveRequest`; a proposed inject whose fields that schema would clear -- ATT&CK techniques without an attribution, a threat actor outside the scenario -- is refused with `ASSISTANT_PROPOSAL_INVALID` naming them, since accepted it could never be saved as proposed and would come back to the panel after every save), and the report the form would have: the saved document as a save payload (`payload_from_form`, `payload_from_msel`, which round-trip: re-saving one changes nothing) with and without the proposals, and only the **new** warnings are returned and stored. A refusal is a tool error (`ASSISTANT_PROPOSAL_*`).
- **Limits**: 50 pending per person and exercise, 20 items per call, 20,000 characters per patch. Pending ones are pruned after 30 days, decided ones after 90, by the hourly loop that prunes the activity log. Deleting the exercise or the account deletes them.

- **An MSEL from scratch**: phases (`propose_phases`: name, headline, start and end minute, incident time before it, situation update, key questions, objectives), simulated actors (`propose_actors`: name, type, description, channel, the team role that plays it) and threat actors (`propose_threat_actors`, five at most: a MITRE ATT&CK group of the MSEL's release, copied with its name, aliases and live techniques and `origin: system` as the library's Add does, or a custom one with techniques of that release) are proposed like the rest, new or by code. An inject names its phase, actor and threat actor (`threat_actor`, which sets the attribution) by code or by the id the earlier proposal returned, and depends on it; its report is computed with those rows in place. The MSEL's limits (eight phases, thirty actors, five threat actors) come from its save schema. Meters, rooms and a phase's due objectives stay with the Planner.
- **The session plan** (`services/assistant/proposals_prep.py`): `propose_eeg_points` proposes observation points, a new one on an objective's EEG (by its code: `eeg_id` in the patch) or a change of one by `point_id`, with text and P/S/M/U criteria; checked against `ConductPrepSaveRequest` and the plan's report like the rest. A seeded point's text follows its source (the save rewrites it), so only its criteria are proposed, and it can't be deleted from the plan either: the save keeps a seeded point, which leaves only with its source (`ASSISTANT_PROPOSAL_NOT_UPDATABLE`, naming the success criterion, the inject's expected action or the notification requirement to change instead); only custom points are deleted. Dates, people, evaluators, logistics and READY aren't in the schema. A plan not opened yet or read-only answers `ASSISTANT_SESSION_PLAN_NOT_OPEN` / `ASSISTANT_SESSION_PLAN_NOT_EDITABLE`. The page keeps a new point's key through the save (`keepPointKeys`, by position) so the panel finds it saved.
- **Closing a document** (`tests/test_assistant_closing.py`):
  - **Schemas** are published with every `$ref` inlined (`_inline_refs`): a client that doesn't resolve `$defs` still sees each field and enum.
  - **Delete**: `delete: true` with a row's code (`point_id` for an EEG point) proposes removing it (`operation: delete`, empty patch); nothing else may go with it. Applied with what named it: a need leaves its objectives' links, an actor or threat actor its injects; a phase is refused while it holds injects (pending deletions and moves count). The page removes the row; it's saved once gone from the saved document, and `…/applied` then takes the row's id (409 while it's still saved).
  - **Dry run and balance**: every `propose_*` takes `dry_run` (check and measure, keep nothing) and answers `impact: {adds, resolves, added, resolved}` against the report before; `propose_scope` adds `impact_on_msel` (`ttx_msel_service.draft_report(..., scope=)`).
  - **Pending proposals count** (`include_pending`, default true): the before report is the document with the person's pending proposals on it (`_with_pending`, in creation order, skipping any that no longer fit), and the MSEL's recipients are measured against a pending scope.
  - **Lists merge by delta on the server too** (`patch_row`), as on the page.
  - **Named after it was accepted**: a proposal id the client still uses after the person accepted that proposal (they may while the client keeps proposing) names the row it made (`_decided_row`: its `applied_row_id`, or an update's row); a discarded one is refused, saying so.
  - **Dependencies across documents**: an inject proposal whose recipients are in scope only through a pending scope proposal depends on it (`_scope_deps`); discarding the scope discards it too.
  - **No field dropped silently**: an inject proposal whose fields the save would clear is refused with the reason per field (techniques need an attribution, a poll has no objectives...).
  - `list_my_proposals` returns each one's `code`, `depends_on` and a summary written by the server when the client gave none (`auto_summary`).
- **Governance and changesets**:
  - Every result about an exercise carries `classification: {tlp, handling}` (`tools.classification`), the TLP of its needs analysis and one line on what may leave the organization; the client is bound by it.
  - Accepting (`…/applied`) or discarding a proposal is recorded in Platform's activity log (`assistant.proposal_accepted` / `assistant.proposal_discarded`, target kind `exercise`, details: kind of row, operation, the row's code, the proposal's id; never its content). This is the authorship record: the person validates.
  - **Changesets**: every `propose_*` takes `changeset`, a name for proposals made over several calls (`AssistantProposal.changeset`, migration `afb394540659`); `list_my_proposals` filters by it. The panel shows a changeset as a section with its name and Accept these / Discard these for all of it, rows grouped inside as elsewhere.
- **The guide to close documents** (`services/assistant/fixes.py`): every issue of `get_validation_report` carries its `fix` -- `{by: assistant, tool, field}` or `{by: you, where, what}` (a code's own fix first, then the section and field: an MSEL scenario field is `propose_msel_settings`, a recipient outside the scope `propose_scope`...) -- and the report adds `root_causes`, the issues grouped by code, field and section, most first. **`plan_to_ready(ttx_id, document)`** turns the blocking ones into ordered steps: the assistant's grouped by tool in the order proposals build on each other (`TOOL_ORDER`: scope, needs, objectives, MSEL settings, phases, actors, threat actors, injects, EEG), then the person's with where, and the approval or READY step after; warnings apart.
- **MSEL coverage**:
  - `expected_actions` on an inject's change are the whole new list and replace its own (`session_plan_note` counts the observation points seeded from replaced actions, which lose their source).
  - A contingent inject takes `fires_at_minute` and its anchor: `branch_from` (inject code or proposal id), `branch_action` (an expected action's code, or its number on a proposed inject: the page keys a proposed inject's actions `proposal:<id>:<n>`), `rejoin`.
  - `propose_msel_settings` (target `msel_meta`, one row: the MSEL): title, `players_summary` (the MSEL's `summary`, what the Players read: named apart so it never becomes the proposal's own `summary`, its reason), `exercise_start`/`incident_start` (HH:MM), `incident_date`, `duration_minutes`, `time_compression`, `meters` (the whole list; existing ones keep their key by name, new ones get one, returned in `meter_keys` for `poll_impacts`). The content language is the exercise's, not proposed.
  - **Code resets**: `propose_msel_settings` takes `reset_codes` (`phases`, `injects`, `threat_actors`): one proposal per kind (target `msel_renumber`, patch `{kind}`), only on a draft and for kinds out of order (`get_msel`'s `codes_out_of_order`, the read's `renumberable`), and only once nothing pending would move the order again: refused while a contingent inject is unanchored (anchoring moves it behind its parent in the storyline) or proposals on the MSEL's rows are pending, so codes are reset once; `plan_to_ready` adds it as a last step (`codes`), once the injects are final and before they're validated and the session plan updated. It's an action, not an edit: on the page Accept runs the MSEL's own reset (`useRenumberCodes`, the frozen-versions dialog first when there are any), never part of Accept all, blocked while changes wait to save; the panel marks it applied once the saved MSEL shows the kind in order, and `…/applied` refuses it before (409).
  - **Supersession**: a new update covering every field of an older pending one on the same row, or a deletion of that row, discards the older (`superseded` in the answer).
- **Polls**: `propose_injects` takes `format`, `poll_question`, `poll_options`, `poll_outcomes` and `poll_impacts` (by option, a meter's key from `get_msel`'s `meters` → level). Meters themselves aren't proposed: the Planner sets them.

**Finding them** -- the header, before the glossary, shows the assistant's spark and how many of the person's proposals wait on the exercise in context, only while some do; it opens a list of where (Needs analysis, MSEL, Session plan, After-action report), each a link (`components/layout/AssistantPendingMenu`, `hooks/useAssistantPending`: the list endpoint as a background request, read again after any write of the page -- `DATA_CHANGED_EVENT` from `apiFetch` --, on window focus and every 15 s while the tab is visible, so proposals the AI client makes appear without reloading; an open panel reads them in on `PROPOSALS_ARRIVED_EVENT`). The Creator menu's counts are another thing: the validation issues keeping each document from moving on, whatever their origin (`GET /ttx/{id}/attention`). Each page's panel also opens with "Also waiting: MSEL (12)", links to the other sections; a changeset says how many of its proposals wait on another page; a proposal that needs one waiting elsewhere says "Accept first: …, in <section>".

**On the page** (`components/assistant/ProposalsPanel.tsx`, in the needs analysis, MSEL and session plan editors and the after-action report): a panel above the form lists the person's pending proposals for that page — read on load and when the tab comes back into view, no polling — each with its summary, the fields (the saved value struck through on an update) and the warnings it adds.
- **Accept** merges it into the page's draft (`lib/proposals.ts`: `mergeNeedsProposals`, `mergeMselProposals`, which takes phases, actors and threat actors before the injects that name them, `mergeConductPrepProposals`) through the editor's own `update()`, so it behaves like an edit: past DRAFT the editor asks first (withdrawing the approval, reopening a READY MSEL) and Accept stays off while that question is open; a read-only MSEL keeps it off with the reason. A proposal with dependencies is accepted with them ("Accept with 1 linked proposal"). Rows are found by id (`target_id`), never by key; ids of phases, actors and needs are translated to the page's keys. An update whose field the page changed since (it differs from `base` and from the proposal) asks before replacing it.
- **Saved by the autosave**: once the saved document holds the row (a created row's key now has an id; an update's fields match), the page calls `POST …/applied {row_id}` and the proposal leaves the list. Undoing or removing the row, or cancelling the editor's question, puts it back to pending. Fields match whatever the order of an object's keys (a patch comes back from JSONB with them sorted, a saved row in its schema's order) and, for link lists (`objective_ids`, `due_objective_ids`, `linked_need_keys`), of their members; other arrays keep their order. `tests/test_assistant_msel_rows.py` pins the contract: every kind of proposal, applied as the page does and saved, reads back holding its patch.
- **A brake, so nobody loops**: accepting an update the saved document already holds marks it applied at once (`heldBySaved`), with no save in between. One accepted on the page that comes back to pending although its row is saved is shown as **Already saved** with one action, **Close**, which marks it applied to that row; if the server refuses (`ASSISTANT_PROPOSAL_ROW_NOT_SAVED`), the reason is shown and **Discard** offered. It's never asked for approval again. An accepted deletion whose row is still there after a save the page saw go through (`ATTENTION_CHANGED_EVENT`) reads **Kept by the form**, with Discard.
- **Discard** discards it and the pending proposals that depend on it.
- **All at once**: with more than one to decide, the panel's header offers **Accept all (N)** -- every one, each after the ones it needs, in a single merge, so the editor asks its question once and one autosave saves them -- and **Discard all**, after a confirmation. Past three proposals each one's changes fold behind "N changes", so the list reads as titles and summaries. **By item**: the proposals on one saved row (INJ-27), changes and deletions alike, are shown together under its name, and an EEG's observation points under their objective ("EEG of OBJ-01"), new, changed or deleted: first, when they all change the same row, **Result of accepting them**, what the ticked ones do to it field by field, then each one with a checkbox (ticked at first) labelled by its reason (or "Proposal N" without one) and its own change; the group's **Accept these (N)** / **Accept selected (N)** and **Discard these** / **Discard selected** decide them, and those left behind are ticked again. A new row stands on its own.
- **Lists add up**: on an update, a list field (recipients, objectives, key questions, techniques...) is merged by what the proposal adds and takes out against its `base` (`patchRow`), not replaced, so two proposals adding recipients to one inject both land; it reads as saved when the row has what it adds and lacks what it removes, and never raises a conflict. Lists show as `+ member` / `− member`.
- **Names, not internals**: fields take the panel's labels, else the form's own (`creator.msel.fields`, `creator.needs.fields`); closed values theirs (attribution, format, actor type, channel...); a row another pending proposal creates reads as its name, "Sandworm Team (proposed)", never `proposal:<id>`.
- **Warnings in words**: the page passes its own wording of validation issues (`issueMessage`: `useNeedsIssueMessage`, `useMselIssueMessage`, `useConductPrepIssueMessage`), so a proposal's warnings read as the form's, without the row's name it's already under; a bare code only where a page has none.
- API (session cookie, CSRF on writes, author only; a Planner or the Lead Evaluator, and a Program Manager reads the list): `GET /ttx/{ttx_id}/assistant/proposals?status=&target=` (each with `outdated`: an update whose row changed or went since), `POST /ttx/{ttx_id}/assistant/proposals/{id}/applied {row_id}` (the row must be saved in the exercise, and be the update's own; 409 `ASSISTANT_PROPOSAL_ROW_NOT_SAVED`), `POST /ttx/{ttx_id}/assistant/proposals/{id}/discard` (returns every id discarded). A decided proposal answers 409 `ASSISTANT_PROPOSAL_DECIDED`.

## After-action report

The report's authors, its Planners and its Lead Evaluator (`after_action_service.can_write`, as on the report's page), draft it with the client. A Lead Evaluator who doesn't plan reaches this and nothing of the design: `list_exercises` lists their exercises with `you_plan: false`, and `get_msel` still refuses them. Nobody else reads a session here, a Program Manager off the team and a Controller who doesn't plan included.

- **Reads** (`services/assistant/session_record.py`): `get_after_action_report` (the report, with its TLP) and `get_session_record` (injects played or skipped, expected actions and their marks, decisions, polls with what followed, meters, ratings, the team's notes, the feedback form's results; `sections` narrows it). Always the report's own run, through the same readers as "From the session" and the exports: the feedback keeps its minimum of answers and a Player's notes stay out. People aren't named, only their role: the screens show who, but a report is about capabilities, and no name needs to leave the server for it.
- **Proposals** (`services/assistant/proposals_aar.py`), each with the page's flow above: `propose_report_text` (`aar_text`: executive summary, scenario, conclusions), `propose_objective_assessments` (`aar_objective`: strengths, areas for improvement, analysis, by objective code) and `propose_improvement_actions` (`aar_action`: new or by code: objective, finding, action, owner, area).
- **Evidence, mandatory**: a report records what happened, so every item cites what of the session backs it (`evidence: [{kind, ref}]`, with `kind` one of `inject`, `action`, `decision`, `poll`, `rating`, `note`, `feedback`). The server checks each against the record (`evidence_index`; 409 `ASSISTANT_PROPOSAL_UNKNOWN_EVIDENCE`) and keeps it with its label (`AssistantProposal.evidence`), and the panel shows it under "Based on". Feedback under its minimum can't be cited. It proves the reference exists, not that the text follows from it: reading that is the person's.
- **What stays with people**: an objective's level (the evaluation team's judgment: a suggested one anchors whoever reviews it) and an action's dates, status and re-test. The tools' schemas have no such fields, so a client sending them is refused.
- **On the page** (`AfterActionSection`, for whoever can edit): the same `ProposalsPanel`, merged by `mergeAarProposals` into the report through its own `edit`, so the autosave persists it and `AAR_STALE` applies as usual. The report's texts count as one row, keyed by the report's id; a new action carries a page-only `key` until it has one. Accepting on a FINAL report asks first, since it reopens it as the next version.
- **Moving the report to another session** discards its pending proposals: they cite the session it left (`after_action_service._discard_proposals`).
- **The notice**: version 2 names a session's records. A tool states the version that covers it (`ToolSpec.notice`), and a token acknowledged under an older one gets `ASSISTANT_NOTICE_OUTDATED` from these five tools and keeps working on the rest, until the person creates a new one.
