# Instance tenancy (open / single / managed)

A deployment decides who may found organizations: any account (`open`), one organization (`single`), or only the ones its operator creates, e.g. one per subsidiary (`managed`). **A fresh deployment is `managed` with at most one organization** (`tenancy_service.DEFAULT_POLICY`) until the environment or the instance administrator says otherwise — so nobody can found an organization on a new install until its operator completes the [first run](#first-run).

## Modes
| Mode | Who founds organizations | Register screen | Avatar menu / Waiting Room |
|---|---|---|---|
| `open` | any account (`POST /organizations`, `POST /organizations/mine`), capped per account by `MAX_ORGANIZATIONS_PER_PROGRAM_MANAGER` | plain / token / *Set up my organization* | *Create your own organization* |
| `single` | the first one only — whoever founds it first, self-service or from Platform — then nobody | plain / token (org choice until the first exists) | hidden once it exists; Waiting Room names the organization of the email's domain |
| `managed` (default, max 1) | only an instance administrator, from Platform | plain / token | hidden; same Waiting Room hint |

`max_organizations` caps the whole deployment in `open` and `managed`; `single` ignores it (1 by definition — Platform hides the field). A stricter rule, or a cap below today's count, **never deletes anything**: it only stops new organizations.

## Choosing a rule
| Deployment | Rule | Why |
|---|---|---|
| Public / SaaS-like instance, many unrelated teams | `open` (optionally with a cap) | Anyone founds their own; the cap bounds the instance |
| One company, installed by the person who will run it, not reachable by others before setup | `single` | No console step: the installer signs up with *Set up my organization* and becomes its Program Manager |
| One company, operated by IT, reachable before the business owner is ready | `managed`, max 1 (the default) | Nobody can take the organization first; IT names its first Program Manager |
| Group with N subsidiaries | `managed`, max N (or no cap) | Only the operator creates each subsidiary and names its Program Manager |

### `single` vs `managed` with max 1
Once the organization exists they behave the same: no more organizations, newcomers matched by domain. They differ only in how the first one is born and how the rule grows:

| | `single` | `managed`, max 1 |
|---|---|---|
| Who founds the first organization | **Anyone**: the first account to choose *Set up my organization* (signup) or *Create your own organization* (avatar menu) | **Only an instance administrator**, from Platform |
| Needs console access to the server | No | Yes, once: `scripts.instance_admin grant` |
| Risk | Whoever reaches the deployment first owns the organization — a race if it's reachable before setup | None: self-service founding is closed from the start |
| Going to N subsidiaries later | Change the mode to `managed` | Raise the cap (Platform or `.env`) |

Rule of thumb: `single` is the quick install where the installer is the first user; `managed`, max 1 is the controlled install — hence the default.

## Where the rule comes from
Resolved by `tenancy_service.effective_policy`, first match wins:
1. **Environment**: `TENANCY_MODE` (+ `TENANCY_MAX_ORGANIZATIONS`) in `.env` pins it. Platform shows it read-only with a note; `PUT /instance/settings` answers 409 `TENANCY_PINNED_BY_ENV`. Use it for infra-as-code deployments or to keep the rule out of anyone's hands. Applies on backend restart (`docker compose up -d backend`).
2. **Web**: the `instance_settings` singleton row (`id = 1`), saved by an instance administrator in Platform. Applies immediately.
3. **Default**: no env pin and no row → `DEFAULT_POLICY` (`managed`, max 1).

`require_self_service_founding` gates the two self-service paths (before any account is created: a refused signup leaves no account behind), `require_instance_founding` the Platform path. While a cap applies, founding takes a transaction advisory lock so two concurrent signups can't both take the last place.

## Free email domains (`open` only)
Under `open`, an account founding its own organization (signup's *Set up my organization*, the avatar menu's *Create organization*) needs a work email: `org_creation_security.validate_organization_signup` refuses a free email domain (422 `FREE_EMAIL_DOMAIN_BLOCKED`) and a domain with neither MX nor A record (422 `DOMAIN_NOT_ROUTABLE`; a DNS timeout or error lets it through). Those accounts can still sign up with *Create my account* and join organizations. Under `single` and `managed` nothing here applies — the operator picks every founder, including from Platform's *Create organization* — and `ORG_CREATION_DOMAIN_POLICY_ENABLED=false` switches it off everywhere.

The list = `BUILTIN_FREE_EMAIL_DOMAINS` (in the code, grown by releases) minus the built-in ones switched off, plus the ones the instance administrator added (`free_email_domain` rows: `disabled` marks a switched-off built-in domain; an added one is deleted, never disabled). **Platform → Tenancy rule** shows it as a second panel only while the saved rule is `open`, with a description saying it has no effect under the other rules: add a domain, switch a built-in one off and on (adding a switched-off built-in domain switches it back on), remove an added one (Undo toast). Each change asks for a recent authentication and is recorded (`free_email_domain.add`/`.remove`/`.enable`/`.disable`, the domain as target). The API answers under any rule (`applies` says whether it's `open`), so the list can be prepared before switching.

## First run
On the default rule nobody can found an organization by themselves. The operator:
1. Opens the app and registers an account with *Create my account* (it lands in the Waiting Room — expected).
2. Grants it from the server: `docker compose exec backend python -m scripts.instance_admin grant <email>`.
3. Signs in again; enrolls TOTP (mandatory for an instance administrator).
4. Avatar menu → **Instance administration**: *Create organization* with its name and the email of an existing account, which becomes its Program Manager and Planner (it can be the operator's own account, or the business owner's once they've registered). Or change the rule there first (e.g. raise the cap for subsidiaries, or switch to `open`).

To pin a rule instead, set it in `.env` before the first start, e.g.:
```env
TENANCY_MODE=managed
TENANCY_MAX_ORGANIZATIONS=5
```
or `TENANCY_MODE=single` (installer signs up with *Set up my organization*, no console step), or `TENANCY_MODE=open`.

Local development: `seed_demo` forces `open` for its own run; set `TENANCY_MODE=open` in your `.env` to keep founding open while you work. The test suite runs on `open` (conftest swaps `DEFAULT_POLICY`; tenancy tests set their own rules).

## Changing the rule later
- From Platform (if not pinned) or `.env` + restart. Existing organizations, members and exercises are untouched.
- `open` → `single`/`managed` with several organizations already: all stay; only new founding stops (count ≥ 1 / ≥ cap).
- Lowering a cap below today's count: same — nothing is deleted, founding stays closed until the count is below the cap.
- Pinning in `.env` overrides whatever was saved from the web; unpinning brings the saved row (or the default) back.

## Instance administrator
`User.is_instance_admin` — the deployment's operator, above any organization (it doesn't join the ones it creates; give it a role there like anyone else if it should work inside one). Granted and revoked from the web (Platform → Accounts, on the account's page, below) unless `INSTANCE_ADMIN_WEB_GRANTS=false` leaves it to the server's console, which works in every case: `docker compose exec backend python -m scripts.instance_admin grant|revoke|list [email]` on an existing account (the first administrator always comes from there — see [First run](#first-run)). TOTP mandatory (`require_instance_admin` → 403 `INSTANCE_ADMIN_REQUIRED` / `MFA_REQUIRED`; the frontend's mandatory-TOTP gate counts `is_instance_admin`). All writes need CSRF. Changing the rule (`PUT /instance/settings`) and deleting an organization also ask for a recent authentication (step-up, TOTP); creating and editing organizations skip it on purpose (the user's call: routine operator work).

**Deleting an instance administrator's account** (Preferences → Delete account) is never blocked — it's the person's right — and breaks nothing: organizations, members, exercises and the saved rule stay. The account is deactivated and anonymized like any other, and its grant is cleared (`deactivate_account` sets `is_instance_admin = False`), so `scripts.instance_admin list` only shows active administrators. If it was the last active one (`/auth/me` `is_last_instance_admin`), Preferences warns before the confirmation: afterwards nobody can manage Platform until someone with console access grants another account (`instance_admin grant <email>`).

**Platform** (`/platform`, avatar menu → *Instance administration*, visible only to instance administrators) is the operator's own workspace: the module shell (Header, section menu with its fold, content cap; `components/layout/PlatformLayout.tsx`) without being one of the organization's modules — it sits above every organization, so the ContextBar shows *This instance › Instance administrator* with nothing to pick, and it's not in the Role selector. Sections (`PLATFORM_SECTIONS`, one file each in `components/platform/`, shared bits in `platformCommon.ts`; menu order: **Tenancy rule**, **Accounts**, **Organizations**, then Legal documents, Email, Sign-in security, Single sign-on, Activity log; `/platform` opens Organizations; the old `/platform/admins` leads to Accounts filtered to administrators): **Tenancy rule**, **Accounts** ([Managing an account](#managing-an-account), [Granting and revoking administrators](#granting-and-revoking-administrators)), **Organizations** (name, domain, Program Managers, created), **Legal documents** (`docs/features/legal-documents.md`), **Email** (how the instance sends email: the server's configuration, read-only, or set here; test message, periodic reconfirmation of addresses and outbox — `docs/architecture/email.md`), **Sign-in security** ([Sign-in security](#sign-in-security)), **Single sign-on** (the identity provider people may sign in with: the server's configuration, read-only, or set here; redirect URI, provider test — `docs/architecture/sso.md`), **Activity log** ([Activity log](#activity-log)). Each section is a page title (with its action, e.g. *+ Create organization*) and a folding description, then its list in an untitled panel — the project's list pattern: count, a status/action filter where it helps, `TableToolbar` search and sort, pagination in the footer, all of it in the URL (`useTableUrlState`, `useUrlFilter`). Organizations, Accounts and Activity log search, sort and page **on the server** (`q`, `sort_by`/`sort_dir`, `limit`/`offset`: an `open` SaaS instance can hold thousands). Defaults are newest first. Accounts has a filter bar of four combined selects — status (active / suspended), organization (one, or *No organization*), role (Program Manager, Planner, Evaluator, Observer: held in the organization picked, else in any; a disabled grant doesn't count) and instance administrator (yes / no), in the URL as `?status=&organization=&role=&admin=`, with *Clear filters* — and sorts by registration, name or last sign-in. Its columns: Account (name, email), Organizations and Roles (one line per organization in both, so each organization's roles sit level with it; a disabled membership struck through with *Disabled*), Instance admin (a check), Status (a dot and *Active* / *Suspended*), Last sign-in; the log searches who acted and what was acted on, filters by action and sorts by date. An instance administrator with no role in any organization lands on Platform from `/` instead of the Waiting Room; from Platform, the logo goes back to the organization's work (the module page left before Platform, else the default workspace) — Platform is never the remembered workspace. *Create organization* takes a name and the email of an existing active account, which founds it exactly like a self-service founding (`_found_organization`: Program Manager + Planner, its email domain seeded as allowed domain); no confirmation. It's disabled, with a note, while the rule leaves no room (`single` with its one, or the count at the cap). Each row's Actions:
- **Edit** — the organization's **domain** (`set_organization_domain`: a Program Manager can't change it; the new domain joins the allowlist for both grants if missing, the old entry stays) and its **Exercise Program Managers**: add by email (`grant_program_manager`: existing account, domain allowed for Program Manager — 404 `USER_NOT_FOUND`, 403 `DOMAIN_NOT_ALLOWED`, 409 `ALREADY_PROGRAM_MANAGER`), remove (`revoke_program_manager`, never the last one: 409 `LAST_PROGRAM_MANAGER`). Name, profile, people and everything else stay in the organization's own Admin.
- **Delete** — the organization's name typed to confirm, plus step-up (TOTP) like every irreversible action, then `delete_organization` (the same full cascade as the Program Manager's delete in Admin → Organization; irreversible).

## Sign-in security
**Platform → Sign-in security** (`PlatformSecuritySection.tsx`, `GET`/`PUT /instance/security-policy`, step-up on save, recorded as `security_policy.update` with before/after) keeps two decisions in the `instance_settings` row, defaults = the rules before it existed (`security_policy_service.DEFAULT_*`); no environment pin.
- **Passwords**, on top of the fixed floor (`StrongPassword`: 8 characters, lower/upper/digit/symbol): minimum length 8–64, refuse the account's name or email local part, no reuse of the last N (0–24, the current one counted; `password_history`, only kept while N > 1, pruned on each change, removed with the account), maximum age 1–730 days or never (`User.password_changed_at`, set by `set_password`; existing passwords count from the migration). New rules apply to the next password set; an expired one locks the account to `/auth/...` with `PASSWORD_CHANGE_REQUIRED` until changed. Platform's temporary passwords are long enough for the minimum and never enter the history.
- **Second factor by role**: Program Manager, Planner (the whole planning and control team), Evaluator, Observer, Player (`InstanceSettings.mfa_required_*`); the instance administrator always, not a choice. Applies at once: `core/security._require_mfa_for` on every guard, `/auth/me`'s `mfa_mandated` for the enrollment gate, and disabling TOTP is refused while a held role needs it. Each role shows how many active accounts holding it have no TOTP yet. A code by email never meets the mandate; a single sign-on with the provider's MFA does (per session).

## Managing an account
**Platform → Accounts** is for *finding* the person. **+ Create account** (`POST /instance/accounts` `{email, full_name}`, step-up, `Cache-Control: no-store`, recorded as `account.create`; 409 `EMAIL_ALREADY_REGISTERED`) makes one whatever the tenancy rule, with no organization (roles come from an organization's Admin, the administrator grant from its page) and a **temporary password** shown once, like a reset: the first sign-in only reaches the password change. Its address isn't asked to be confirmed (`email_verification_required` stays false: the operator vouches for it). Each row has one action, **Manage** (pencil), which opens their account at `/platform/accounts/:userId` (`components/platform/PlatformAccountDetail.tsx`; the list's filters ride along in the router state, so *← Accounts* returns to them). Everything is done there, one panel per decision, from the most frequent to the gravest; confirmation grows with the consequence.

- **Header**: name, email, badges (instance administrator, suspended, two-factor on/off, must choose a new password), registered and last sign-in.
- **Account details** — name and email (`PATCH /instance/accounts/{id}`; email lowercased and unique, 409 `EMAIL_ALREADY_REGISTERED`; no step-up, like editing an organization; recorded as `account.update` with before → after). Changing the email changes how the person signs in, and which organizations match them by domain.
- **Where they work** (read-only) — their organizations (roles, *disabled*, *its only Exercise Program Manager*) and exercises (`CodeRef`, organization, the context roles they hold, Lead Planner / Lead Evaluator). Changed in each organization's Admin or exercise team, never here.
- **Sign-in and security** — each ends every session of the account, asks for a step-up and is recorded:
  - **Reset password** (`POST …/reset-password`, `Cache-Control: no-store`, `account.password_reset`): it works whether or not the deployment sends email, so the server generates a **temporary password** (16 characters, one of each class `StrongPassword` asks for, no look-alike characters; `account_admin_service.temporary_password`) returned **once** — Platform shows it with *Copy* until *Done*, and tells the operator to hand it over a trusted channel. It sets `User.password_change_required`: the temporary password signs in (two-factor still asked) but every route except `/auth/...` answers 403 `PASSWORD_CHANGE_REQUIRED` until the person chooses their own on `/account/password` (`RequiredPasswordChange`, the ordinary `POST /auth/password`; reusing the temporary one is 422 `PASSWORD_REUSED`). The frontend's `needs-password-change` status comes before the legal and two-factor gates.
  - **Reset two-factor** (`POST …/reset-two-factor`, `account.totp_reset`): for a lost or replaced phone — secret, backup codes, anti-replay step and lock cleared. Where the account's roles make two-factor mandatory, the mandatory-TOTP gate has them enroll again before anything else.
  - **Sign out everywhere** (`POST …/end-sessions`, `account.sessions_end`): a lost or shared device; password and two-factor unchanged.
- **Access** — instance administrator (grant / revoke with the rules of [Granting and revoking administrators](#granting-and-revoking-administrators); hidden while web grants are off) and sign-in (suspend / reactivate, [below](#suspending-an-account)).
- **Delete for good** (`DELETE /instance/accounts/{id}` `{confirmation}` = the email, step-up, `account.delete`) — **only an account that left no trace**. `account_admin_service.dependencies` walks every foreign key to `user.id` in the metadata and counts its rows, by category (organization roles, exercise seats, join/leave requests, invitations created or redeemed, library items, exercise content — designed, noted, rated, signed —, changes to the instance); any → 409 `ACCOUNT_HAS_DEPENDENCIES`, and the panel lists them and points to suspending instead. A table missing from `DEPENDENCY_CATEGORIES` counts as *other* and also blocks (better keep an account than leave rows pointing nowhere); `tests/test_account_admin.py` fails when a new reference isn't classified. Deleting re-checks with the account row locked, removes its sessions, backup codes, legal acceptances and uploaded avatar, keeps Platform's log (`actor_user_id` set to NULL, `actor_label` keeps the email) and frees the email for a new account. Never an instance administrator (409 `REVOKE_INSTANCE_ADMIN_FIRST`, so the "never the last one" rule holds). Different from Preferences → Delete account, the person's own deactivation and anonymization, which works whatever the dependencies.
- **Several at once** (the list's checkboxes; the header one takes the page, the selection is kept across pages and cleared after acting; your own row has none): a bar *N selected* offers **Suspend**, **Reactivate**, **Sign out everywhere** and **Delete for good** (`POST /instance/accounts/bulk` `{action, user_ids ≤ 100, confirmation}`, step-up; suspending and deleting ask for the number of accounts typed). Each account is done on its own and recorded as if done alone; the refused ones (your own account, the last instance administrator, one with dependencies, one gone meanwhile) are skipped, not fatal, and the dialog lists them with the reason. Resetting passwords or two-factor and granting administrator stay one at a time, on the account's page: each hands something to a person.
- **Your own account** is shown (how others see it) but not managed here: every action answers 409 `CANNOT_MANAGE_YOURSELF` and the page points to Preferences — no locking yourself out with one click.

## Suspending an account
**Platform → Accounts** lists every active account of the deployment (search by name or email, its organizations with roles there). Only an instance administrator suspends one, in every tenancy mode: an account belongs to no organization, and a Program Manager's reach stays their own organization (Users and roles → Remove, which disables access there only).

- **Suspend** (the account's page → Access; the email typed, step-up): `User.suspended_at` set (`account_suspension_service.suspend_account`). Every session ends at once (`revoke_sessions`, which also closes the Playground stream) and a login waiting on its second factor can't finish. Password login answers 403 `ACCOUNT_SUSPENDED` — only after the right password, so it doesn't reveal which emails are suspended; `get_current_user` treats the account as signed out.
- **Nothing is deleted**: grants, exercise seats, notes, ratings stay; the email stays taken (no new account with it). **Reactivate** (restore icon, step-up) clears `suspended_at` and everything is back.
- Different from `is_active=False`, the self-service deletion that anonymizes the account for good; deleting someone else's account isn't offered.
- Never your own account (409 `CANNOT_SUSPEND_YOURSELF`) nor the last active instance administrator (409 `LAST_INSTANCE_ADMIN`). A suspended administrator doesn't count as active (`is_last_instance_admin`, `scripts.instance_admin list` marks it).
- **Organizations it alone runs**: the dialog names those where it's the only active Program Manager (`sole_program_manager`) — they're left without one until Platform → Edit names another. Typical in `open`, where every account founds its own.
- A suspended account can't be made Program Manager from Platform (create or grant: 409 `ACCOUNT_SUSPENDED`) and leaves *From your domains, without a role*.
- From the console, when no administrator can sign in: `docker compose exec backend python -m scripts.instance_admin suspend|unsuspend <email>`.

## Granting and revoking administrators
`instance_admin_service`, shared by the web and the console.
- **Grant** from the account's page (Accounts → Manage), which shows who the person is: *Make instance administrator*, the email typed, step-up (`POST /instance/admins` `{user_id, confirmation}`). An active, unsuspended account only (409 `ACCOUNT_SUSPENDED`, `ALREADY_INSTANCE_ADMIN`). It has to enroll TOTP before Platform opens for it (`require_instance_admin`). Not offered on your own row nor on accounts that already hold it.
- **Revoke** from the account's page too (`DELETE /instance/admins/{user_id}`, the email typed, step-up): anyone but yourself in the web (an account's page doesn't manage your own; the endpoint and the console still allow it), while another active, unsuspended administrator remains (409 `LAST_INSTANCE_ADMIN`; the active ones are locked `FOR UPDATE` before counting). Takes effect on the next request — the grant is read from the DB each time, no session to end.
- **`INSTANCE_ADMIN_WEB_GRANTS=false`** (`.env`, backend restart): both answer 409 `INSTANCE_ADMIN_WEB_GRANTS_DISABLED`; `GET /instance/admins` says `web_grants_enabled: false`, the account's page shows the console command instead of the buttons. The console (`scripts.instance_admin`) ignores the switch: it's the way back. Default `true`. A hardened SaaS operator may set it to keep the grant a server-side act; with it on, the activity log is the counterweight.

## Activity log
`PlatformAuditEvent` (`platform_audit_event`), written by `platform_audit_service.record` right after each action succeeds (services commit on their own: a crash in between can leave an action unrecorded, never a recorded one that didn't happen). **Append-only**: no endpoint or service edits an entry; entries older than **90 days** (fixed; Platform → Activity log → Retention shows it, read-only) are deleted once forwarded — the SIEM and `auth.log` keep the full history (`docs/architecture/logging.md`). Read in Platform → Activity log (`GET /instance/audit`, `limit`/`offset`/`action`/`q`/`sort_dir`, newest first; the action filter groups *Sign-in and account* and *Administration*; failed attempts read in the danger colour).
- **Recorded**: `tenancy.update` (before → after), `free_email_domain.add`/`remove`/`enable`/`disable` (the domain), `organization.create` (its first Program Manager), `organization.domain` (before → after), `organization.delete`, `program_manager.grant`/`revoke` (from Platform), `account.suspend`/`reactivate`, `instance_admin.grant`/`revoke`, `legal.publish` (version), `legal.acceptances_export` (it lists every account), `email.settings_update` (before → after, never the password), `email.settings_delete`, `email.test` (recipient, outcome), `sso.settings_update` (before → after, never the secret), `sso.settings_delete`, `sso.test` (outcome). Also the organization and exercise work that asks for no step-up (the "Organizations and exercises" group of the filter): `organization.create` from the avatar menu, `organization.leave`, `organization.allowed_domain` (op, domain, scopes), `organization.role_invited`/`role_invitation_withdrawn` (the address, roles), `organization.role_invitation_accepted`/`role_invitation_declined`, `organization.delete` from Admin, `library.item_delete`, `exercise.delete`, `exercise.member_joined`, `exercise.needs_approved`, `exercise.needs_approval_recorded`, `exercise.scenario_applied`, `exercise.aar_final`/`aar_reopened` — who and what, never the content. Legal drafts and templates aren't (work in progress, not decisions). The console's suspend / unsuspend / grant / revoke are recorded with `actor_user_id = None` and `actor_label` `console` ("Server's console"). Also every account's **authentication events** (`auth.*`: sign-in and its failures, second factor, step-up, sign-out, sign-up, password and two-factor changes — the list in `docs/architecture/logging.md`).
- **As it read at the time**: `actor_label` (the actor's email) and `target_label` (email, organization name, document kind) are copies, and `target_id` has no FK — deleting an organization keeps its history. **Deleting an account doesn't anonymize the log** (`deactivate_account` leaves it): it keeps who did what with the email of the time, the one exception to anonymization while an entry is kept, stated in the privacy-policy template (§2 and §6, *Activity log*).
- **Download** (`GET /instance/audit/export?format=jsonl|csv`, the list's `action`/`q`; oldest first; step-up, since it lists accounts; itself recorded as `audit.export`): JSON Lines, one event per line with the fields `id, time (ISO 8601 UTC), action, actor_id, actor, target_kind, target_id, target, details` — what a log shipper (Filebeat, Fluent Bit, a SIEM's file input) ingests as is — or CSV (same columns, `details` as JSON; cells starting `= + - @` are prefixed with `'` against formula injection).

### Forwarding to a SIEM
Platform → Activity log → *Forward to a SIEM* streams every **new** entry to the SIEM's HTTP collector as it happens (earlier ones: download them).
- **Set up** (`PUT /instance/audit/webhook` `{url, enabled, authorization}`, step-up, recorded as `audit_webhook.update`): the collector URL — `https://` only, with a host and no `user:password@` (credentials go in the optional **Authorization** header, e.g. `Splunk <token>` for Splunk HEC, `ApiKey …`/`Bearer …` for Elastic or a gateway; stored, sent with each delivery, never returned: `has_authorization`; `""` removes it, omitted keeps it). `AUDIT_WEBHOOK_ALLOW_HTTP=true` (`.env`) also accepts `http://`, for a collector inside the operator's network only. A **signing secret** is generated on creation (shown in Platform, *New secret* replaces it: `POST …/webhook/rotate-secret`, step-up, recorded). *Remove forwarding* (`DELETE …/webhook`, step-up, recorded) drops the queue; the log stays. *Send a test entry* (`POST …/webhook/test`, not recorded) posts one synthetic `audit_webhook.test` event and shows the answer.
- **Delivery**: `POST <url>`, `Content-Type: application/json`, body `{"source": "ttx-zone", "events": [<event as in the JSON Lines download>, …]}` (up to 100 per request), headers `X-TTX-Zone-Timestamp` (Unix seconds) and `X-TTX-Zone-Signature: sha256=<hex HMAC-SHA256 of "<timestamp>.<raw body>" with the secret>` — the collector recomputes it, compares in constant time and may reject old timestamps. Redirects are never followed; 10 s timeout; any 2xx is success.
- **Guarantees**: an **outbox** — `record` queues the event (`PlatformAuditDelivery`) in the same commit while forwarding is on, and a background loop started with the app (`forward_forever`, every `AUDIT_WEBHOOK_POLL_SECONDS`, default 10) sends the queue **oldest first**; rows are taken `FOR UPDATE SKIP LOCKED`, so several backend processes can run it. A failure (network, non-2xx) keeps the batch and retries its head with a growing delay (20 s doubling to 1 h), so events arrive **at least once and in order** — a collector should de-duplicate by `id`. Paused (`enabled: false`) nothing new is queued; what's queued waits. Platform shows the state (`pending`, last success / failure, last status and error).


## Newcomers in `single` / `managed`
No roleless membership exists (one `OrganizationMembership` per grant), so a newcomer is matched by domain instead:
- the account registers with *Create my account* (its subtitle, `auth.register.choosePlainSubtitleManaged`, says to ask the organization's Exercise Program Manager for a role -- every grant needs an existing account, so this is the only door for staff); the Waiting Room calls `GET /instance/domain-organizations` and tells them which organization to ask (or that the deployment's administrator creates organizations, if no domain matches);
- Admin → Users and roles shows **From your domains, without a role** (`GET /organizations/{id}/domain-accounts`): active accounts whose email domain is on the org's allowlist (any purpose) and hold no grant there; *Give a role* opens Add person with the email filled.

Both answer empty in `open`: there anyone can found an organization claiming any domain, so they would leak names and accounts. For the same reason, in `open` a Program Manager grants roles directly only within the organization's own domain or to its members; anyone else is invited and accepts from their account (`docs/features/admin.md` → Invitations to the organization). Even in `single`/`managed` the match trusts the email the account declares: it's confirmed only on a deployment that sends email (`docs/architecture/email.md#account-links`). There, an account with its confirmation pending stays out of *From your domains, without a role* until it confirms.

## Troubleshooting
| Symptom | Cause / fix |
|---|---|
| No *Set up my organization* at signup, no *Create your own organization* in the avatar menu | The rule closes self-service founding (the default does). Check `GET /api/v1/instance/policy` |
| Nobody can manage Platform after the last instance administrator deleted their account | Grant another existing account from the server: `scripts.instance_admin grant <email>` |
| "This account is suspended" at sign-in | An instance administrator suspended it: Platform → Accounts → Reactivate, or `scripts.instance_admin unsuspend <email>` |
| Forwarding shows *Failing* with entries waiting | The collector refuses or is unreachable (the badge names the status or error): fix it and the queue drains in order on its own; *Send a test entry* checks it at once |
| An account's page shows a console command instead of *Make instance administrator* | `INSTANCE_ADMIN_WEB_GRANTS=false` in `.env`: grant from the console, or remove the line and restart the backend |
| No *Instance administration* in the avatar menu | The account isn't an instance administrator: `scripts.instance_admin list` / `grant <email>`, then sign in again |
| Platform shows the rule read-only | `TENANCY_MODE` is set in `.env`: change it there and restart the backend |
| *Create organization* is disabled in Platform | The cap is reached (or `single` already has its one): raise the cap or change the mode |
| *Create organization* answers "account not found" | The Program Manager's email must belong to an existing, active account: have them register first |

## Frontend wiring
`/auth/me` carries `is_instance_admin` and `can_found_organization`; the register screen (anonymous) reads the public `GET /instance/policy`. Menus hide what the rule closes; the server refuses regardless. `/account/organizations/new` sends a closed deployment home.
