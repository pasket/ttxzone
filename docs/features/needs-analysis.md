# Creator → Needs analysis

The first design artifact of an exercise (ISO 22398 / NIST SP 800-84: needs analysis → SMART objectives → scope) and the **design gate**: until the form is `APPROVED`, the MSEL can't be created (`GET /ttx/{ttx_id}/msel` → 409 `NEEDS_FORM_NOT_APPROVED`) and an existing MSEL is read-only. Menu entry and page title: **"Needs analysis"** (ISO 22398's name for the whole stage); section 3 is "Identified needs". Players never reach it; a Program Manager of the org can, via the guard's bypass. All endpoints `RequiresOrgAndTTXAccess(RoleEnum.PLANNER)`.

## Model
- `TTXNeedsForm` — 1:1 with `TTX`; sections 0–2/4/6–8 as columns, multi-selects as `ARRAY(VARCHAR)` of StrEnum values; `stop_exercise_keyword`, TLP, participating areas and third parties, never-reused `NEED-NN`/`OBJ-NN` counters, `revision`, `version`, `status`. **Renumbering**: while the form is a first draft (`DRAFT`, version 1, no MSEL yet) `POST …/needs-form/renumber` (`kind`: `needs`|`objectives`) rewrites that kind's codes — needs **in creation order** (their current numbers, since the counter never goes back: it only closes the gaps deletions left, whatever the list order; `_renumber_order`), objectives **in needs order** (by the lowest NEED code each one covers, none last, ties in creation order) — resets its counter and rewrites the codes named in the form's free text (`code_renumber.py`, one pass); `codes` (row id → code, the `previous` a renumber returned) undoes it. `NeedsFormRead.renumberable` lists the kinds that would change (needs: only with gaps); the Needs step then shows "Renumber by creation date", the Objectives step "Renumber in needs order" (disabled while unsaved; Undo toast).
- `TTXNeed` (`title` — a short name, how the table, objective links, the traceability matrix, the PDF and every message name it (`needName`: title, else finding); `finding` — the description; a blank title is `NEEDS_FORM_INCOMPLETE`; migration `d4a7e2b9f381` took the first sentence of existing findings as title when ≤ 80 chars and left the rest as finding), `TTXObjective` (+ `TTXObjectiveNeed` N:M; `title` — a short name, required (blank is `NEEDS_FORM_INCOMPLETE`), how lists, references, headings, messages and PDFs name it (`objectiveName` / backend `objective_text.objective_name`: title, else statement), while the `statement` stays the full SMART sentence shown under it wherever it is rated or read whole (objectives table, EEG, needs PDF, SitMan); migration `b5e1d7c2a904` added it empty, also on `ConductPrepEegObjective` (the plan reads the live title first); `regulatory_requirement_ids` from `app/data/regulatory_catalog.py`; `success_criterion` holds **one observable condition per line** — each line one EEG observation point — and `evidence` one item per line (`services/objective_text.py`, client twin `textLines` in `lib/needsForm.ts`); `achieve_at_least` (null = all conditions, clamped to 1..N−1 on save), `time_box_minutes` (from the inject that triggers it) and what each outcome means, read with the common P/S/M/U scale — `achieved_note` (P or S; a note on the rule the conditions make, which is derived, never typed), `partially_achieved` (M), `not_achieved` (U); never points — migration `a8d3f1c6e529` moved "Partially/Not achieved …" and lead-in lines out of the criterion, `c3f8a2d6e715` split that free guidance into the three levels (`objective_text.split_levels`)), `TTXExerciseRisk`, `TTXNeedsFormApproval` (per `version`; recorded by an Exercise Planner on the approver's behalf — `recorded_by_id`/`recorded_at` — a status mark, not a signature), `TTXNeedsFormEvidence`.
- **Invariant: every TTX has a `code` and a form**, both created by a SQLAlchemy `before_flush` hook in `ttx_needs_form_service` (so fixtures building `TTX(...)` get them too). `TTX.code` = `TTX-YYYY-NN`, sequential per org and UTC creation year under a row lock on the organization, unique per org. `create_ttx` adds three default exercise risks in the request locale (`get_locale`), the `default` entries of `app/data/risk_catalog.py`.
- **Add from the library** (`components/creator/needs/NeedsLibraryPicker.tsx`, `lib/needsLibrary.ts`, tests `test_objective_catalog.py`, `NeedsLibraryPicker.test.tsx`): the Objectives step offers TTX-Zone's SMART objective templates (`app/data/objective_catalog.py`, `GET /objective-catalog`: two per capability, bilingual, each with a title, statement, one observable condition per line free of the vague words and rating levels the validation flags, evidence, regulatory requirement ids and an optional time box) for the capabilities ticked; one pick opens the objective dialog prefilled, still to be linked to a need. The Risks step offers TTX-Zone's exercise risks (`app/data/risk_catalog.py`, `GET /risk-catalog`, by category: confidentiality, people, operations, logistics, conduct of the session); ticked ones become rows, a risk already in the form shown ticked and disabled. Both copy the text in the exercise's `content_language` (else the UI's); nothing is stored about where it came from.
- `TTXRead` carries `code`, `needs_form_status` and `tlp` (batch-loaded in `GET /ttx`).

### Regulatory catalog (section 2)
`FRAMEWORK_CATALOG` in `regulatory_catalog.py`: 12 frameworks by jurisdiction (EU, ES, UK, US, GLOBAL), each with localized label/name/scope, `requires_exercises` (a "Requires exercises" tag), `binding` (False = contractual, e.g. PCI DSS) and `rationale_*` + `rationale_reference` (why a tabletop suits it — shown only for ticked frameworks, printed as a table in the PDF). Plus `OTHER`, never a catalog entry, with required free text `regulatory_framework_other`. A requirement's `framework` is a framework id when it belongs to one (localized client-side via `frameworkLabel`), else a display name (ISO). `GET /regulatory-requirements` serves the catalog. `NOTIFICATION_MILESTONES` marks the **notification requirements** (NIS2 Art. 23, DORA Art. 19, GDPR Arts. 33–34, CER Art. 15, UK NIS Reg. 11, SEC 8-K 1.05, NYDFS § 500.17) with their reports — recipient, stage, deadline, when the clock starts, en/es — served as each item's `notifications`. **Expected notifications** (`services/notification_reference.py`, client twin `lib/notifications.ts`) are derived, never stored: every cited notification requirement once, in catalog order, with the objectives citing it. `common/NotificationReference` shows them under the Objectives table (`design`: live from the draft) and in `EegView` (`observe`: what to note — the clock is simulated, so recognising each report, not meeting it). Dropping one = unticking the requirement in its objective.

## Save model
- `GET`/`PUT /ttx/{ttx_id}/needs-form` saves the **whole form**: collections full-replaced keyed by id (needs and objectives keep their ids — injects and the EEG link to them); new rows get codes from the counters; objectives reference needs by payload `key`.
- `PUT` rejects (422) only what can never be stored: V01 ≤ 4 capabilities / ≤ 5 objectives (`NEEDS_FORM_LIMIT`), V02 `OBJECTIVE_WITHOUT_NEED`, V04 `OBJECTIVE_CAPABILITY_NOT_SELECTED`. An objective the MSEL links (inject or phase) can't be removed: 409 `OBJECTIVE_IN_USE` naming the codes.
- Everything else is the **validation report** returned by every read: `validation.ready` blocks → `READY_FOR_APPROVAL`, `validation.approved` additionally blocks → `APPROVED`, `warnings` never block (V06 orphan HIGH need; vague success-criterion words in en/es; V10 `REGULATORY_OBJECTIVE_SUGGESTED`, only a warning when OTHER is the only regulation named; `CONDITION_IS_A_RATING_LEVEL` (a condition line that reads as a rating level or lead-in); V11 `OBJECTIVE_FRAMEWORK_NOT_NAMED`, once per framework an objective cites but Triggers doesn't name — section 2, `item_id` the framework; its fix names it in Regulations, turning the regulatory trigger on if needed). Each issue has `code`/`section`/`field`/`item_id`. A rejected transition is just 409 `NEEDS_FORM_INVALID` (the detail is in the report; the error envelope stays single-code).
- An objective's **success criterion is written only here**: each clause (`eeg_service.observation_points`) becomes a read-only `criterion` point of the conduct prep's definitive EEG, which adds only how it is rated (P/S/M/U). Changing it means re-approving and "Update the EEGs" there (`docs/features/conduct-prep.md`).
- `POST …/needs-form/validate` = **dry run** (`draft_report`): the same report for an unsaved payload, saving nothing; rows named by id when saved, by payload `key` otherwise (objectives/risks accept an optional `key` for this); V01/V02/V04 and `objectives_in_use` reported as issues instead of errors. `validation_report` is duck-typed to serve stored rows and previews.
- `revision` bumps on every write (stale → 409 `NEEDS_FORM_STALE`). `version` is the document version: **any edit** past `DRAFT` returns the form to `DRAFT` — leaving `APPROVED` opens version N+1 (old approvals kept as history), leaving `READY_FOR_APPROVAL` drops that version's approvals.
- Transitions `POST …/needs-form/transitions`; → APPROVED needs no step-up and is recorded as `exercise.needs_approved`.

## Approvals and evidence
- `POST`/`DELETE …/needs-form/approvals[/{approval_id}]`: only while `READY_FOR_APPROVAL` (no step-up; recording one is logged as `exercise.needs_approval_recorded`). Recording again for the same approver **corrects it in place** (keeps its evidence).
- **Evidence** (`ttx_needs_form_evidence_service`): files backing an approval (signed PDF, approval email) — ≤ 5 per approval, 10 MB each, PDF/PNG/JPEG/WEBP/DOCX/XLSX/EML/MSG/TXT checked by extension *and* leading bytes, stored under `settings.NEEDS_EVIDENCE_UPLOAD_DIR` with random names, **never StaticFiles-mounted** (TLP content). Download only through `GET …/approvals/{approval_id}/evidence/{evidence_id}` (`attachment`, allowlisted content type, `Cache-Control: private, no-store`). Attachable while READY or APPROVED (signed copies often arrive later; doesn't bump `revision`), removable only while READY. Files are unlinked in an `after_commit` hook (dropped on rollback) wherever their rows go: approval removed, leaving READY, org cascade delete.

## PDF export
`GET /ttx/{ttx_id}/needs-form/pdf[?lang=en|es]` (`needs_pdf_service.render_needs_pdf`, reportlab with bundled Vera fonts; copy in `needs_pdf_labels.py`): every section, the traceability matrix, a signature block per approver (sponsor, design lead, compliance if applicable; names prefilled from recorded approvals), the wordmark in every page header (`pdf_common.draw_logo`, vectors from `logo-modo-light.svg`'s geometry — no image/SVG dependency), TLP label top **and** bottom of every page (FIRST TLP rule), a not-approved notice unless APPROVED. With required items missing (`validation.ready` not empty; missing approvals don't count — that's what it's signed for) it still exports, as a **draft for review**: "DRAFT – NOT VALID FOR APPROVAL" banner top and bottom of every page, how many items are missing on the first, and `_DRAFT` in the name (`{code}_v{version}[_DRAFT]_{TLP}.pdf`), `attachment` + `no-store`. The page's button is disabled only while there are unsaved changes; with items missing it reads "Download draft PDF", described by "N items missing: it downloads as a draft. Go to the first" (the link opens the first missing item in on-screen section order). The Approval step suggests signing the complete PDF and attaching the signed copy as evidence.

## Markdown export
`GET /ttx/{ttx_id}/needs-form/export.md[?lang=en|es]` (`needs_markdown_service.render_needs_markdown`): the same sections, order and copy as the PDF (`needs_pdf_labels`, plus `pending`), for a wiki or a repository. The TLP label opens and closes it; a draft carries the PDF's banner and notice at the top and `_DRAFT` in its name (`{code}_v{version}[_DRAFT]_{TLP}.md`); approvals are listed as recorded (signatures stay the PDF's job). Every user value goes through `md()`: a backslash before the characters that would become emphasis, code, a link, a table cell break or raw HTML, and before a heading/quote/list marker at the start; line breaks folded. `text/markdown`, `attachment`, `private, no-store`, `nosniff`; same guard as the PDF (`DESIGN_ENDPOINTS`). The page offers it next to the PDF ("Markdown", disabled while there are unsaved changes).

## Frontend
`components/creator/needs/CreatorNeedsFormSection.tsx`; section `needs` (`/creator/:ttxId/needs`, second in `CREATOR_SECTIONS`). Creating an exercise lands here. `CreatorDesignGate` stands in front of the MSEL until `needs_form_status === 'approved'` (or an MSEL exists, `msel_status`).
- **One section at a time** (`?step=`, `lib/needsForm.ts`'s `NEEDS_STEPS` + read-only `OUTPUT_STEPS`; shown order ≠ section number: "Capabilities to evaluate" (section 4) comes right after Triggers, before the needs — `goToIssue` finds a step by `index`, never by position); a warning shown in one section but fixed in another offers a one-click fix under it (`issueFixes`: a HIGH need with no objective → "Fixed in Objectives: create an objective that answers it", opening a new objective linked to it; a capability with no objective; an objective whose capability isn't ticked). The needs table is always grouped — by capability (default) or by priority, `?group=priority` — each group by code, the grouped column hidden; one toolbar line (Group by left, Add need right); fixed column widths (no sideways scroll). The objectives table follows the same pattern — by capability (default) or by the need it answers (`?group=need`: every need by code, empty ones say no objective answers them yet, an objective linked to two needs shows under both); the worked objective example lives in the step description's "Show more" (`HelpText`'s `extra`). The whole form is one draft (`NeedsFormDraft`, `draftFromForm`/`payloadFromDraft`; rows carry a `key` — the id, or `newRowKey()` — which is how objectives link needs). Previous/Next and the section list only navigate.
- **Autosave, no Save button** (a separate Save next to Next confused users). Machinery in `hooks/useAutosavedDocument.ts` (shared with the MSEL): saves `AUTOSAVE_DELAY_MS` (800 ms) after the last edit, only once the live report was computed for that exact draft (`live.payload === payload` — a slow check must never let a refused draft through) and has no `SAVE_BLOCKING_CODES`; never two saves at once (the revision bump reschedules); a failed dry run shows as "Couldn't save…" until the next check succeeds.
- `baseline` (the draft matching the saved form) is kept apart from `draft`; after a save `reconcileSaved(sent, next)` becomes the baseline (ids/codes from the server, keys and link order from what was sent); edits typed during the save survive (`adoptSavedIds` only hands new rows their ids, so nothing is created twice).
- Past DRAFT the first edit asks "withdraw the approval?" (once per status + version), then autosaves too. A stale save toasts with Reload. The panel's `aside` shows `SaveStatus` (Saving… / All changes saved / Unsaved changes / Not saved: fix… / Couldn't save), hidden on output steps.
- **Live report**: while dirty the draft is posted to the dry run (400 ms debounce); section counts, `SectionIssues`, the summary and red fields read it (the saved form's report otherwise; `ApprovalStep` uses the saved one since transitions act on the saved form). Issues point at rows by draft `key`. Each section opens with its own issues (a red count must explain itself where the user is looking); messages via `hooks/useNeedsIssueMessage.ts` (lookup in `creator.needs.validation.*`, since `code`/`field` are plain backend strings). Shared lists: `common/IssueSummary.tsx` (`IssueSummary`/`SectionIssueList`), `common/SaveStatus.tsx`.
- Left column: the section list (issue count per section) and `ValidationSummary` (To submit / To approve / Warnings; each entry focuses its field or opens the row dialog).
- Steps: `SimpleSteps.tsx` (sections 0/1/2/4/6/7). Scope (6) has three numbered groups — Level, Scope (perimeter / out of scope side by side) and **Participants**, with a note that the MSEL builds on it (no group is tinted or framed in the accent: emphasis goes in words): participating areas are the injects' recipients and the expected actions' responsible areas, and optional third parties (outside organisations taking part) can receive injects too (`MselNeedsContext.third_parties`, accepted by M09, a separate group of recipient chips and an `<optgroup>` of responsibles). `NeedsStep`/`ObjectivesStep`/`RisksStep`: table + `RowDialog` (`Modal size="lg"`, Cancel/Done in a footer that stays in view while the dialog scrolls). The objective dialog is `size="xl"`, the form at full width; **Evaluator view** (a toggle by the title, `RowDialog`'s `aside`) floats a live preview over the right of the form, sticky while it scrolls (Escape folds it first; remembered for the tab) -- Why (linked needs; the first one ticked suggests the capability until it is picked by hand), What (title + statement + capability), How it's measured (`LineListEditor` of numbered conditions: Enter adds a row, Backspace on an empty one removes it, a multi-line paste becomes rows; per-row assists split "(1) … (2) …" into rows -- the lead-in goes to the guidance, a "N minutes" in it to the time box -- or move a rating-level line to the guidance; "Achieved when" All N / At least K of N; time box; **How to rate it**: three rows — Achieved · P/S (the derived rule + an optional note), Partially achieved · M, Not achieved · U; the condition assist moves a level line to its row, prefix dropped), Evidence (one item per row), Regulatory requirements (optional, a selected count; `RegulatoryPicker`: a height-capped table with an accent-insensitive search and a scope switch: Triggers' frameworks / All / Selected). `RowDialog` asks in its footer before Cancel, Escape or a backdrop click discards edits (`dirty`); a need an objective links can't be removed; unticking a capability an objective uses just surfaces `OBJECTIVE_CAPABILITY_NOT_SELECTED`. `ApprovalStep`: submit / record approvals / approve / back to draft / reopen, all disabled with unsaved edits. `OutputSteps.tsx`: traceability matrix (`lib/needsFormOutputs.ts`) and the EEG (`GET /ttx/{id}/eeg`, shared `EegView`: the derived draft, or the ready conduct prep's definitive EEGs).
- `common/TlpBadge` draws the label FIRST-style (coloured mono text on black, `--color-tlp-*` — never for severity/status). Creator → Exercise's identity band shows code, TLP and form status.

## Acronyms and glossary (every screen, every role)
- `lib/glossary.ts` (`GLOSSARY_TERMS`; expansions/explanations in the top-level `glossary.terms.*` keys). Add a term to the list and both locales together.
- `common/AcronymText` marks terms up as `<abbr title>` (dotted underline, WCAG H28, no tab stops) in labels, legends, options, hints, step descriptions and intros — app copy only, never user content.
- `common/GlossaryPanel`: the keyboard/touch route, opened from `Header`'s "?" button (left of the avatar, also in Preferences) or the `?` key outside text fields. **Non-modal** right-side panel (`role="dialog"` without `aria-modal`, below the logo row, full screen on mobile) with search and the terms found in `#main-content` first ("On this page", re-read by a `MutationObserver`). Not filtered by role (static vocabulary). Open state local to `Header`; `?glossary=EEG` deep-links and highlights on first render. No per-page glossary buttons.
