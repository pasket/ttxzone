# Creator → Exercise

## Exercise profile (`CreatorExerciseSection`, `/creator/:ttxId/exercise`)
- The first ttx-scoped Creator section (a bare `/creator/:ttxId` lands here): the **profile of the active exercise only**, mirroring Admin → Organization. No exercise list — the ContextBar is the picker (`/creator/exercises` redirects to `/creator`). Keyed by `ttxId` in `CreatorSectionOutlet`; an id the user doesn't manage redirects to `/creator`.
- View: `CreatorExerciseDashboard` "Exercise profile" with an identity band (image or initials, name, description, created date, code, TLP, needs form status, Lead Planner, tags, **Edit exercise**). Creating or deleting an exercise isn't done from inside one: see Exercises below.
- Edit (`?edit=1`) keeps the band read-only and shows, in order: `ExerciseForm` (details + tags, one Save), then the immediate-apply `ExerciseTeamPanel`. The page owns the exercise's tag list (fetched only while editing) and feeds all three; tags themselves are managed in Library → Tags.
- `ExerciseForm` serves create and edit: name, **content language** (`TTX.content_language`: the language its injects and material are written in, never anyone's interface language; new exercises start in the creator's — the select's default and, left out, the request's `Accept-Language` —, a scenario applied to it sets it to the scenario's, Planners change it; null for an exercise from before it was recorded, the select then asks; what's written for the table by default — ENDEX — follows it), description (full panel width, `common/FormattedTextArea`: Bold / Italic / bulleted and numbered list buttons, Cmd/Ctrl+B/I, a Write / Preview switch; stored as a small Markdown subset, ≤ 10 000 chars on the API, shown through `common/FormattedText`, which builds React elements and never injects HTML), square image, tags (hidden when the vocabulary 403s), all staged until one Save: `POST /ttx` (with `organization_id`) or `PATCH /ttx/{ttx_id}` → image `POST`/`DELETE` → tags `PUT` (only if changed).
- **Exercises** (`CreatorExercisesSection`, literal `/creator/exercises`, org-scoped): reached from the ContextBar's exercise selector ("All exercises"), not from the Creator menu, which lists the exercise picked in the ContextBar (Exercise, Needs analysis, MSEL, Session plan, After-action report, Players) and then, after a hairline, the Library. The page: **+ New exercise**, the list of the exercises the Planner works on (`ttxOptionsForModule('creator')`: code and name, needs/MSEL status, Lead Planner, created; Open sets the context; search/sort in the URL), over the organization overview (KPIs, exercises per week; org-scoped Planners only). A Planner with no exercise lands here (`routeForContext`, `/creator/exercise` redirects).
- **Delete** (`DELETE /ttx/{ttx_id}`, body `{confirmation}` = the exact name, no step-up, recorded as `exercise.delete`): the exercise's Lead Planner (still a planning member) or a Program Manager of its organization (`ttx_service.can_delete_ttx`; `TTXRead.can_delete` shows the trash icon only to them; others 403 `TTX_DELETE_FORBIDDEN`, wrong name 422 `CONFIRMATION_MISMATCH`). Permanent: `ttx_service.delete_exercises` (shared with the organization delete) removes tokens, access requests, tag assignments, the team, tags, session plan, MSEL and images, needs analysis and evidence, clears users' default exercise, and the image file after commit. The dialog offers "Export it as a scenario first".
- **Duplicate** (`POST /ttx/{ttx_id}/duplicate` `{name, organization_id}`; `common/ExercisePortfolio`'s `DuplicateExerciseModal`, from a row of Exercises and the identity band's **Duplicate**, offered on an exercise the user plans when they're also an org-scoped Planner): a new exercise in the same organization, its name typed (default "… (copy)"), the dialog saying what comes along and what doesn't. `ttx_service.duplicate_ttx`, one transaction: `create_ttx(commit=False)` (new code, the duplicator its Lead Planner, Planner who controls), the source's image copied to a new file, the team (`_copy_team`), then `scenario_service.export_ttx` → `apply_document` on the copy -- so it carries exactly what a scenario does (needs analysis, MSEL with injects and images, cast, threat actors, tags, rooms; `docs/features/scenarios.md`), with the needs analysis and MSEL as fresh DRAFTs, no people, dates or approvals, and the source's library origin (`scenario_origin*`). The description is kept whole (the scenario format caps it lower). **Team**: every Planner / Evaluator / Observer row (never Players), each with the functions their active org grants still allow -- Planner functions need the Planner grant, `evaluates` / an Evaluator row the Evaluator grant, `observes` the Observer grant (never both; Evaluator wins), the Lead Evaluator flag kept on whoever still evaluates; a Planner who lost the grant but still evaluates/observes becomes an Evaluator/Observer; anyone left with nothing (or an inactive account) is skipped and named in `skipped_members` (the toast lists them). The duplicator's own flags (facilitates, evaluates, observes, leads) carry over too. Not copied: Players, invitations, access requests, leave requests, runs, the session plan, the after-action report, tags on people. A failed check (`report.ok` false) rolls everything back and unlinks the copied image: 422 `TTX_DUPLICATE_FAILED`. The copy becomes the active exercise and opens on its profile.
- **Archive** (`POST /ttx/{ttx_id}/archive` / `…/unarchive`; `ArchiveExerciseModal`, the box icon on a row of Creator → Exercises and Admin → Exercises, for whoever may delete it — `can_delete`; a plain confirmation, it's reversible): `TTX.archived_at`/`archived_by_id`. An archived exercise is **read-only** — the server refuses every write with 409 `TTX_ARCHIVED` (`docs/architecture/rbac-and-multi-org.md`) except duplicating it and following up its improvement plan; no session starts, nobody joins (invitations, email invitations, Join), Players can't ask to leave. Refused while a session is live or paused (`RUN_IN_PROGRESS`). The UI: both lists show Active exercises by default with a **Show** filter (Active / Archived / All, URL `archived`; Admin passes it to `GET /ttx?archived=`), an "Archived" badge on the row (neutral); the ContextBar's selector lists archived ones last in an "Archived" group (`ttxOptionsForModule`/`ttxOptionsForRole` order them last, so a "first available" pick lands on one in play); inside one, `ArchivedExerciseBanner` (one line under the header in Creator, Control and Execution, with Unarchive for those who may), no Edit on the profile, the needs analysis doesn't take edits, MSEL / Session plan / after-action report read-only from their `editable` / `can_edit` (the report's action status stays changeable, `can_follow_up`), and Control offers no Start or Restart.
- **Create** (`CreatorExerciseCreateSection`, literal `/creator/exercises/new`): from Exercises' + New exercise and the ContextBar's "+ Create exercise" link (no exercise yet); on save `refresh()`, make it active and open its needs analysis. Cancel hidden for a first exercise.

## No exercise selected (`CreatorNoExerciseSection`, literal `/creator/exercise`)
Someone managing an exercise is redirected to `/creator/{activeTtxId}/exercise`. An org-scoped Exercise Planner managing none (where `RequireTtxParam`, `contextEntry` and `routeForContext` land them) gets an org-wide overview: a "Create exercise" band, then KPIs from `GET /organizations/{organization_id}/planner-overview` (`require_planner`, `dashboard_service.get_planner_overview`): exercises in the org (+ last 30 days), owned by you (planner row on one you created), co-managed (planner row on someone else's), players, Exercise Planners, exercises created per week. **Aggregates only** — never other managers' exercise names.

Needs analysis, MSEL and Players without an exercise say "Create an exercise first to …" (`CreatorExerciseRequired` on literal `/creator/needs` and `/creator/msel`; with one they redirect to the active exercise's section).

## Exercise team (`ExerciseTeamPanel`, in edit mode)
- Everyone on the exercise except the Players, as a **read-only matrix** (same look as Admin → Users and roles, `common/RoleMatrix`): Person (name, Lead Planner / Lead Evaluator badge, email) · Planner · Controller · Facilitator · Observer · Evaluator · Last login · Tags (the organization's tags on the person first, then the exercise's own) · Actions (make lead, edit, remove). Description = `common/RoleGuide` (intro + each role behind Show more). Search/sort client-side, URL keys prefixed `team_`.
- Backend `/ttx/{ttx_id}/people…` (`ttx_people.py`, `ttx_people_service`, Planner-only): `GET` (rows with `role`, `plans`/`controls`/`facilitates`/`evaluates`/`observes`, `is_lead`, `grants` = what their org grants allow, `org_tags`, `tags`), `GET …/candidates` (org people with an active Planner/Observer/Evaluator grant not on the exercise, with their `grants`), `POST` (email + role + functions), `PUT …/{user_id}/role` (with `evaluates`/`observes` for a team member, each needing its org grant; `?lead_successor_id=` when the lead stops planning), `PUT …/{user_id}/tags`, `DELETE …/{user_id}` (`?lead_successor_id=` for the lead).
- **Edit** (`Modal`) and **Add** share `RolesFieldset`: the person's roles as **one checkbox per matrix column**, in two groups — Design and conduct (Planner / Controller / Facilitator) and Observation and evaluation (Observer / Evaluator) — then Tags. Editing adds the lead choices under their role: "Lead Planner of the exercise" under Planner (the current lead's is ticked and locked: there's always one, so it moves by making someone else lead → `PUT …/planning-team/lead`) and "Lead Evaluator" under Evaluator (optional: `PUT`/`DELETE …/evaluators/lead`); only a lead change, without a role change, skips the role `PUT`. The matrix's flag action stays as the shortcut. Rules applied as you tick: a Facilitator is a Controller (unticking Controller unticks it); Observer and Evaluator are distinct and exclusive — the Observer watches, the Evaluator takes notes and rates with the EEG — so ticking one unticks the other (server: 409 `OBSERVER_OR_EVALUATOR`); each role needs its org grant (Planner for the first three) — without it the box is locked and one footnote lists the missing grants and where they're granted; a role already held stays available; at least one role ("Pick at least one role"). `toRoleRequest` maps the flags onto the API: Planner or Controller ticked → `role: planner` with `plans`/`controls`/`facilitates`/`evaluates`/`observes`; else `evaluator` or `observer`. Adding a team member who also evaluates/observes is a `POST` then a `PUT …/role`. The team's rules are mirrored before Save: never the last Planner or Controller (`LAST_PLANNER`/`LAST_CONTROLLER`), a lead who stops planning names a successor. Changing your own role refreshes the context bar.
- **Add person** (Create pattern): pick a candidate (a select — only authorized people can be added), their role (preset to the first one granted) and tags.
- **Remove**: typed full name; a lead names who takes over; refused up front for the last Planner or Controller. Removing yourself refreshes auth and leaves to `/creator`.

## Rooms (`ExerciseRoomsPanel`, in edit mode, below the team)
Whether the exercise is played in several rooms at once, its rooms and where each Player sits: see `docs/features/rooms.md`. Off by default: a switch and one line, nothing else.

### Lead Planner
- Exactly one member who plans coordinates the team and owns the calendar and deliverables: `TTX.lead_planner_id` — the creator by default (`create_ttx`), reassigned by any Planner to another member who plans (`PUT /ttx/{ttx_id}/planning-team/lead`, returns the whole team; 400 `LEAD_MUST_PLAN`). Successors must plan too.
- **Never handed over silently**: removing the lead or the lead leaving needs `?lead_successor_id=` (on `DELETE …/planning-team/{user_id}` and `DELETE /ttx/{ttx_id}/access`; 409 `LEAD_SUCCESSOR_REQUIRED`, 400 `INVALID_LEAD_SUCCESSOR`); deleting an account that leads exercises needs `lead_successors` (exercise id → member) in `DELETE /auth/me` (`GET /auth/me/lead-exercises` lists them with candidates). The remove modal and Preferences → Privacy preselect the longest-standing member.
- Reads never trust the column alone (`lead_user_id` falls back to the first member; `lead_planners` batches `TTXRead.lead_planner`).
- Shown in the exercise team matrix (`common/LeadPlannerBadge`: flag + "Lead Planner", accent tint — an identity marker, not a status colour; a flag `btnNeutralIconGhost` "Make … the Lead Planner" on other Planners' rows) and the identity band (flag + name).

### Lead Evaluator
- At most one Evaluator per exercise organizes the evaluation team (assignments, evaluator briefing, rated EEGs): `TTXAccess.leads`, on an Evaluator's row (EVALUATOR, or a team member's that `evaluates` — who then gets both flag actions, Lead Planner and Lead Evaluator), one per exercise by the partial unique index `uq_ttx_access_lead_evaluator`. Optional on the exercise; the evaluation plan (Creator → Session plan) requires one before it can be ready.
- Any Planner sets it (`PUT /ttx/{ttx_id}/evaluators/lead` `{user_id}`, 204; 404 `EVALUATOR_NOT_FOUND`; the previous lead stops) or clears it (`DELETE …/evaluators/lead`). It goes with the row: removing the Evaluator deletes it, and `ttx_people_service.set_role` clears it when they stop being an Evaluator.
- Read as `leads` on `ExercisePersonRead` and `EvaluatorRead`; the team matrix shows `LeadEvaluatorBadge` (same look as the Lead Planner's) and the same flag action on other Evaluators' rows.
