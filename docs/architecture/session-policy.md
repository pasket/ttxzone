# Session policy

### Session policy (server-side sessions, timeouts, step-up MFA)
- **`UserSession`** (`app/models/user_session.py`, migration `e271cee0fbd5`; logic in `app/services/session_service.py`): one row per signed-in browser; the access JWT carries its id (`sid`) and `get_current_user_optional` checks it on every request — revoked, idle past `idle_timeout_minutes` (**soft timeout**: `SESSION_IDLE_MINUTES_PRIVILEGED` = 30 for anyone under the MFA mandate — Program Manager/Planner of any org, Planner/Evaluator of any exercise, `session_service.requires_mfa`, resolved at sign-in — `SESSION_IDLE_MINUTES_PLAYER` = 60 otherwise) or past `absolute_expires_at` (**hard timeout**, `SESSION_ABSOLUTE_HOURS` = 12 from sign-in) means no session. Both cookies live until the hard timeout. Every request is activity (`last_seen_at`, written at most once a minute) except those with `X-Background-Request: 1` — mark any future polling/live feed with it, or an open tab never times out — and streams under `…/run/stream` (`session_service.BACKGROUND_PATH_SUFFIX`: an `EventSource` can't send the header). The Playground's stream re-checks the session every `RUN_STREAM_KEEPALIVE_SECONDS` and ends when it lapses (idle, revoked, expired). Every way a session is issued goes through `core/security.start_session` (login, second factor, signup, bare registration, redemption with a new account); never call `set_auth_cookies` directly. At most `MAX_SESSIONS_PER_USER` = 5 (the oldest is ended); ended rows are purged 30 days later, on the user's next sign-in. A token without `sid` (issued before the migration) is refused.
- **Revocation**: logout ends the current session; changing the password, disabling TOTP or confirming a (re-)enrollment ends every *other* one; signing in with a backup code and deleting the account end all of them. `GET /auth/sessions` (active ones, `current` flag), `DELETE /auth/sessions/{id}` (own only, 404 otherwise; the current one also clears cookies), `DELETE /auth/sessions` (all but the current) back Preferences → Security → **Active sessions** (`ActiveSessions.tsx`, `lib/userAgent.ts`).
- **Step-up** (`UserSession.authenticated_at`, set at sign-in and by `POST /auth/step-up` — a TOTP code when the account has TOTP (never a backup code), else the password; an account with neither, created by single sign-on, steps up at its provider instead, `POST /auth/oidc/step-up` — `docs/architecture/sso.md`): `RequireRecentAuthentication` (a `dependencies=[...]` entry) or `require_recent_authentication(current)` answers 403 `REAUTHENTICATION_REQUIRED` unless that was within `STEP_UP_MINUTES` = 15. Guarded: **the account's own credentials** — change password, disable TOTP or the code by email, regenerate backup codes, `DELETE /auth/me`, create a personal access token, link/unlink single sign-on — and **Platform** (instance-wide, the highest privilege): `PUT /instance/settings`, `PUT /instance/security-policy`, Platform's `DELETE /instance/organizations/{id}` (also its name typed), its account actions (create, reset password or two-factor, end sessions, suspend/reactivate, delete, grant/revoke instance administrator), email, single sign-on, AI assistant and legal settings, the activity log's download and forwarding. Not guarded on purpose: **organization and exercise work** — the person is already signed in (with the second factor their role requires) and each of these is recorded in the activity log instead (`platform_audit_service.record` / `record_exercise`, who and what, never the content): founding an organization (`organization.create`), leaving one (`organization.leave`, its name typed), allowed domains (`organization.allowed_domain`), offering roles by invitation and answering one (`organization.role_invited`, `organization.role_invitation_withdrawn`, `organization.role_invitation_accepted`, `organization.role_invitation_declined`), deleting an organization from Admin (`organization.delete`, its name typed and checked by the server) or an exercise (`exercise.delete`, its name typed), deleting a free Library item (`library.item_delete`), a Program Manager joining an exercise (`exercise.member_joined`), recording a needs-analysis approval and approving it (`exercise.needs_approval_recorded`, `exercise.needs_approved`), applying a scenario (`exercise.scenario_applied`), marking the after-action report final or reopening it (`exercise.aar_final`/`aar_reopened`); the MSEL and the session plan sign-offs, restarting a run (the word typed) and inject validation (stamps who) never asked for it. Also Admin → Users and roles (granting or revoking any role, removing a person) — the typed full name is the confirmation there; Platform's organization actions (create, change domain, add/remove Exercise Program Managers). Frontend: `apiFetch` catches that 403, asks `lib/reauthentication.ts`'s handler (`common/ReauthenticationHost`, mounted in `App.tsx`; concurrent refusals share one dialog) and resends the request once confirmed.
- **Second factor from the provider**: a single sign-on whose ID token says the provider did MFA (`amr` contains `mfa`, when the configuration trusts it) opens a session with `UserSession.mfa_source = "provider"`, which `core/security.mfa_satisfied` accepts in place of the account's own TOTP on every mandatory-TOTP gate, for that session only (`docs/architecture/sso.md`).
- **Code by email as a second factor** (`email_mfa_service`, Preferences → Security → Code by email): turned on with a code sent to the account's address (which also confirms it), off with step-up. An account may have both it and TOTP; `User.mfa_preferred` is the one a challenge opens on (sign-in, step-up), and the other is a click away ("Use another method"). **It never meets the mandate**: whoever controls the mailbox can already reset the password, so `mfa_satisfied` ignores it and a role whose second factor is mandatory (Platform → Sign-in security; by default Program Manager, Planner, Evaluator, Observer) still needs TOTP (or the provider's MFA); for them it is only another way to answer a challenge. Where it's an account's one factor, the step-up asks for a code, not the password. While the deployment sends no email the factor isn't offered, and an account whose only factor it is signs in with the password alone (`auth.mfa_skipped`, `reason: email_unavailable`) — as email confirmation is skipped then. Platform's "Reset two-factor" turns it off too. Wrong email codes count against the same limits as TOTP's (below). Codes: `docs/architecture/email.md#verification-codes`.
- **Password step hardening** (`login_throttle_service`, table `login_throttle`, shared by every API process): failed sign-ins lock for 15 min past 10 within 15 min for one account from one address, 50 for one account from anywhere, or `LOGIN_FAILURES_PER_ADDRESS` (100) from one address over any accounts (an IPv6 address counts by its /64), with 429 `LOGIN_THROTTLED`, even for the right password. The lowest limit is the account and address together, so one machine guessing wrong on purpose can't lock the owner out; only spreading over five or more machines can, for 15 min, and sessions already open are untouched. Only failures count, so a room behind one address signing in at once isn't refused. The lock is checked before the password, so a locked attempt costs no hashing. The right password clears the account's counts, never the address's (or signing in to one's own account would reset it between guesses); a password reset clears them too. Keys are hashes, built the same whether or not the account exists: neither the lock nor the answer says who has an account, and `verify_password` spends the same time on an unknown account or one without a password, against a hash that's nobody's. The address comes from `FORWARDED_ALLOW_IPS` (`docs/deployment.md` section 4): set wrong, everyone counts as the proxy, and 100 failures lock every sign-in. Each lock is one `auth.login_locked`. `deploy/`'s proxy also caps `/auth/login*`, `/auth/register` and `/auth/password/*` at 30 requests per second per address (burst 300, queued), for what hashes a password without being a failure.
- **Signing up says when an email is taken** (409 `EMAIL_ALREADY_REGISTERED`): it opens a session at once, which can't be answered alike for an existing account, so this stays a way to learn that one email has an account. `login_throttle_service.guarded_signup` keeps it from being used in bulk: 20 such answers within 15 min lock that address's signups for 15 min (429 `SIGNUP_THROTTLED`, every signup, or the answer would still tell), on `POST /auth/register`, `POST /organizations` and a token redemption that creates an account. An email invitation names its own address, so it isn't limited. Each lock is one `auth.signup_locked`. Closing it altogether means a "check your email" signup, which a deployment without email can't do.
- **Second factor hardening** (`totp_service`): anti-replay — `User.totp_last_step`, a code for that 30-s step or an earlier one is refused (also across login and step-up, so tests must not reuse one code twice); every 5 wrong codes withdraw the login challenge (the mfa_pending token's `jti` must equal `User.mfa_pending_jti`, and only the latest challenge counts → 401 `MFA_CHALLENGE_EXPIRED`, `LoginCard` returns to the password step), 10 within 15 min lock the second factor for 15 min (429 `TOO_MANY_ATTEMPTS`, also at the password step for a TOTP account), logged to `auth.log`.
- **Client** (`lib/sessionActivity.ts`, `common/SessionTimeoutWatcher`, mounted in `App.tsx`): tracks the last request (`noteActivity`, shared between tabs over a `BroadcastChannel` together with sign-out/expiry), warns 2 min before the soft timeout (counting one minute early for the server's write throttle) with **Stay signed in** / **Sign out**, announces the hard timeout 10 min ahead, and at either one calls `AuthContext`'s `expireSession` (server logout + the same "Your session has expired" return-to-page flow as a 401). `GET /auth/me` returns `session` (`SessionInfo`). "Remember this device" (skipping TOTP) was deliberately not built.
- **Email confirmation** (`docs/architecture/email.md#account-links`): an account created while the deployment sends email has `User.email_verification_required`; until `email_verified_at` is set by its link, `get_current_user` answers 403 `EMAIL_VERIFICATION_REQUIRED` outside `/auth/...` (after the temporary-password check, before the legal one). Never while the deployment can't send the link. The client's `needs-email-verification` status sends the person to `/account/verify-email`.
- **Periodic reconfirmation** (`docs/architecture/email.md#periodic-reconfirmation`): an account asked to confirm its address again (`User.email_reconfirm_deadline`) and past that date, still unconfirmed, gets 403 `EMAIL_RECONFIRMATION_REQUIRED` outside `/auth/...` (right after the confirmation check). Never while the rule is off or the deployment can't send the link. `/auth/me`'s `email_reconfirmation_overdue` puts the client in the same `needs-email-verification` status; during the grace period `email_reconfirm_deadline` shows a banner under the header.
- **Forgot password**: `POST /auth/password/reset` with an emailed link ends every session of the account and issues none; signing in afterwards asks for the second factor as always.
- **Temporary password** (an instance administrator's *Reset password*, `docs/features/instance-tenancy.md#managing-an-account`): ends every session and sets `User.password_change_required`; `get_current_user` then answers 403 `PASSWORD_CHANGE_REQUIRED` on everything outside `/auth/...` (checked before the legal-acceptance gate) until `POST /auth/password` sets a new one (step-up satisfied by the fresh sign-in; the temporary one can't be reused, 422 `PASSWORD_REUSED`). The client's `needs-password-change` status sends the person to `/account/password` before any other gate.
- **Personal access tokens** (the AI assistant, `docs/features/ai-assistant.md`): a token authenticates **only** `POST /api/v1/mcp`, and that endpoint accepts **only** a token -- `get_current_user` never reads `Authorization`, the endpoint never reads the cookie. A token carries the second factor of the session that created it (`mfa_source`), meets the same account gates as a session (`core/security.enforce_account_gates`: temporary or expired password, unconfirmed or overdue email, legal documents to accept) and stops working when the account is suspended or deactivated or the instance switch is turned off. **`session_service.revoke_sessions` revokes every token of the account** with the sessions it ends -- a password change or reset, a new second factor, "sign out other sessions", Platform ending the sessions, a suspension. Creating one needs a recent step-up (`RequireRecentAuthentication`).
- **Sessions bound to a face** (`UserSession.surface`, `docs/deployment.md` §9): a session opened on the public face (`APP_ROLE=api-public`) works only there, one opened on the internal face only there; `get_current_user_optional` refuses a session of the other face.
