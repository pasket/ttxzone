# RBAC model and multi-organization membership

## Model
A top-down, multi-tenant hierarchy isolated by `Organization`: several exercises (`TTX`) per org, and an N:M user↔exercise relationship populated by approval-gated token enrollment (`docs/features/invitations-and-enrollment.md`). Two grant tables, same shape:
- `OrganizationMembership` (org scope, `OrgRoleEnum`: `PROGRAM_MANAGER`, `PLANNER`, `OBSERVER`, `EVALUATOR`) — a grant table, not a flag, so an org can have several of each, and one person several roles. `disabled_at` marks every grant of a person removed while still on the org's exercises: guards and lookups only count `active_membership()` grants, `require_ttx_role` answers 403 `MEMBER_DISABLED`, and `/ttx` and `/organizations/mine` leave that org out.
- `TTXAccess` (exercise scope, `RoleEnum`: `PLANNER`, `EVALUATOR`, `OBSERVER`, `PLAYER`) — **one row per exercise per user** (`(user_id, ttx_id)` unique). A `PLANNER` row is a member of the exercise's **planning and control team**, and its flags say what they do there: `plans`, `controls`, `facilitates` (≥ one of plans/controls; facilitates ⇒ controls), and — each from the org grant of that name — `evaluates` / `observes`: also the exercise's Evaluator / Observer (the usual Controller/Evaluator of a small exercise). `TTXAccess.context_roles()` turns a row into what its holder can act as (`TTXContextRole`: planner / controller / facilitator / evaluator / observer, or the row's own role); `TTXAccess.is_evaluator` and the SQL `evaluator_access()` / `observer_access()` are the one way to ask "is an Evaluator / Observer here" — never `role == EVALUATOR` alone (except `eeg_service._is_evaluator_of`, which narrows only pure Evaluators: a team member keeps the live EEG). `RoleEnum.ADMIN` stays allocated in Postgres (no `DROP VALUE`) but is never emitted.

The JWT carries only `sub` and `sid`. `GET /ttx` and every guard query these tables fresh per request, so granting or revoking access takes effect immediately (BOLA/IDOR-safe).

## Roles
- **Program Manager** (org scope) — administers one or more organizations: profile, people and roles (Admin → Users and roles, co-Program Managers included), allowed domains, library. **Oversees, doesn't design**: reads every exercise of the org (`RequiresOrgAndTTXAccess` lets them through on `GET`/`HEAD` only) and may delete one (`DELETE /ttx/{ttx_id}`, its own guard), but creates, edits, invites or approves only from a seat on the exercise's team, like anyone else — and needs the org Planner grant for that. They may take that seat themselves (Admin → Exercises → Join, `POST /ttx/{ttx_id}/people/me`): on the planning and control team, or as Observer or Evaluator, each from their org grant of that name. The founder is Program Manager **and** Planner (`organization_service._found_organization`; the Planner grant is an ordinary, revocable one); a co-Program Manager granted later gets Program Manager only.
- **Founding an organization** — where the deployment's tenancy rule allows it (`open`; `single` until its one exists — the default, `managed` with max 1, doesn't), any signed-in account (a Player or Planner elsewhere, or no role at all) founds its own: avatar menu → *Create your own organization* (also linked from the Waiting Room) → `POST /organizations/mine` (`create_organization_for_user`; CSRF, recorded as `organization.create`). Same work-domain rule as the anonymous signup (`validate_organization_signup`: no free-email or non-routable domains; `Organization.domain` = the email's domain) and a cap of `MAX_ORGANIZATIONS_PER_PROGRAM_MANAGER` Program Manager grants per account (409 `ORG_LIMIT_REACHED`). Roles are per organization, so nothing about the account is "promoted"; founding just adds an org where it holds both grants. The anonymous `POST /organizations` (signup) stays for a new account and 409s `EMAIL_ALREADY_REGISTERED` for an existing one. Both paths are gated first by the deployment's tenancy rule (`tenancy_service.require_self_service_founding`, 403 `TENANCY_MANAGED_ONLY` / `TENANCY_SINGLE_EXISTS` / `TENANCY_ORG_LIMIT`); in `managed` only an **instance administrator** creates organizations, from Platform — see `docs/features/instance-tenancy.md`.
- **Exercise Planner** (org *and* exercise scope) — designs exercises: creates them, needs analysis, MSEL, invitations and access requests, planning and control team, Observers and Evaluators.
  - Org-scoped grant: `OrganizationMembership.role == PLANNER`, by a Program Manager by email of an existing account (`POST /organizations/{organization_id}/planners`, domain-allowlisted). This is what lets a new Planner create their first exercise.
  - Exercise-scoped: a `TTXAccess(PLANNER)` row with `plans` — the creator gets `plans` + `controls` (`ttx_service.create_ttx`); others are added to the team from the org's Exercise Planners (`ttx_planning_team_service`).
  - An exercise always keeps ≥ 1 Planner and ≥ 1 Controller (row-locked count, 409 `LAST_PLANNER` / `LAST_CONTROLLER`, also on leaving via `DELETE /ttx/{ttx_id}/access`). The Lead Planner must plan. An existing Player is refused (`ALREADY_PLAYER`), never promoted.
- **Controller** (exercise scope, a team member with `controls`) — runs the exercise: delivers the MSEL injects and keeps the Players in scope. Works in the **Control** module (`/control/:ttxId`); reads the EEG. No design access unless they also plan.
- **Facilitator** (a Controller with `facilitates`; several allowed) — moderates alongside the Players and keeps the focus on the objectives. Acts on the Player landing (`/playground/:ttxId`), identified as Facilitator (`common/RoleBadge`); shown next to the name in the team panel like the Lead Planner.
- **Observer** and **Evaluator** (org grant + exercise assignment) — a Program Manager grants the role in Admin → Users and roles (`/organizations/{id}/observers|evaluators`, any domain); a Planner of the exercise assigns it from those grants (`ttx_observer_evaluator_service`, `GET`/`POST`/`DELETE /ttx/{ttx_id}/observers|evaluators[/{user_id}]` + `/candidates`; 400 `NOT_ORG_OBSERVER`/`NOT_ORG_EVALUATOR` for unknown and ungranted emails alike, 409 `ALREADY_ON_EXERCISE`). Assigning a planning and control team member sets `evaluates`/`observes` on their row instead (409 if they already hold it; 409 `OBSERVER_OR_EVALUATOR` for the other one — a person is an exercise's Observer **or** its Evaluator, never both); removing clears the flag (and the Evaluator lead and evaluation-plan assignments), leaving them on the team. Revoking the org Evaluator/Observer grant clears the flag the same way; revoking the org Planner grant of someone who also evaluates/observes turns their row into an EVALUATOR (else OBSERVER) row (`depart_team`). Both land on the Player landing, identified. Revoking the org grant takes the person off that role on every exercise of the organization (Planner: never the last Planner/Controller, a lead hands over); the same goes for an org Planner revoke.
  - The Evaluator also keeps Execution → Evaluation: `GET /ttx/{ttx_id}/eeg` (`RequiresOrgAndTTXAccess(PLANNER, CONTROLLER, EVALUATOR)`, `eeg_service.build_eeg`, `EEGRead`): objectives with capability, statement, `observation_points`, evidence, expected actions, P/S/M/U scale — **no design fields**. Evaluators get it only once the needs form is APPROVED (409 `NEEDS_FORM_NOT_APPROVED`) and from the latest READY MSEL snapshot; Planners and Controllers at any stage, from the live MSEL. Observers don't read the EEG.
  - Every design endpoint is Planner-only (`plans`); `test_ttx_evaluation.py`'s `DESIGN_ENDPOINTS` asserts 403 for an Evaluator, 403 on every write and no 403 on reads for a Program Manager off the team (and `test_ttx_control_team.py` 403 for a Controller who doesn't plan) — add new ones there.
  - Observers' notes and Evaluators' live ratings are in the Playground (`docs/features/playground.md`).
- **Player** (exercise scope) — Execution only, joined exercises only. TOTP opt-in. Can join with a token at any time and self-unenroll (`DELETE /ttx/{ttx_id}/access`, hard delete; rejoin is clean). Someone on the planning and control team of an exercise can't be its Player (one row per exercise).

**Mandatory TOTP** per role, set by the instance administrator in Platform → Sign-in security (`security_policy_service`, `InstanceSettings.mfa_required_*`; by default Program Manager, Planner — any planning and control team member —, Evaluator and Observer, Player opt-in; the instance administrator always) on every path to the role (org grant, exercise grant, Program Manager read access).

## Guards (`app/core/security.py`)
- **Program Manager**: `require_program_manager_of` (`organizations.py`) guards every `/organizations/{organization_id}/…` Admin route — the org comes from the URL (the ContextBar's selection) and is checked against the caller's memberships. It calls `require_program_manager(session, user, organization_id)` → `is_program_manager(...)`, as does exercise deletion (org taken from the TTX).
- **Planner (org)**: `require_planner(session, user, organization_id)` → `is_planner` for that *specific* org + TOTP. A user can be Planner of several orgs, so `POST /ttx` takes `organization_id` in the body (`TTXCreateRequest`). Never reintroduce an auto-resolving "the Planner's org" helper (`require_planner_org`/`resolve_planner_organization_id` existed and were removed for this reason).
- **Exercise scope**: `RequiresOrgAndTTXAccess(*allowed_roles)` (`RoleEnum` or `TTXContextRole` values) resolves the route's `ttx_id`; on a read (`GET`/`HEAD`) a Program Manager of the owning org passes (mirrors `list_ttx_for_user`'s visibility, MFA-checked); otherwise — every write, whoever asks — requires a `TTXAccess` row whose `context_roles()` include one of `allowed_roles` (`RoleEnum.PLANNER` = the row plans) — **no implicit hierarchy**, each route lists every role it accepts; denial = 403 `TTX_ACCESS_DENIED` with `ttx_id`. The core is `require_ttx_role(session, user, ttx, allowed_roles, *, program_manager_may_read=False)`, reusable when the `TTX` is reached by another key (e.g. token revocation by `token_id`).
- **Archived exercise** (`TTX.archived_at`): read-only. `RequiresOrgAndTTXAccess` refuses every write on it with 409 `TTX_ARCHIVED` (`require_not_archived`, after the role check) unless the route passes `allow_archived=True` — `POST /ttx/{ttx_id}/duplicate` and `PATCH /ttx/{ttx_id}/aar/actions/{code}` (the improvement plan is still followed up); reads always pass. Entry points keyed by something else call `require_not_archived` themselves: invitation-token redemption, email-invitation preview/accept, a Player's leave request, a Program Manager's Join (`POST /ttx/{ttx_id}/people/me`). Self-guarded routes that still work: archive/unarchive, `DELETE /ttx/{ttx_id}`, leaving (`DELETE /ttx/{ttx_id}/access`), invitation revoke/tags (by `token_id`). Read schemas say so: `MselRead.editable`, `ConductPrepRead.editable`, `AarRead.can_edit` / `AarPreviewRead.can_edit` are false on it (`AarRead.can_follow_up` keeps the status follow-up).
- **Library**: `require_library_manager` (writes) — Program Managers only; `require_library_reader` (lists) — Program Managers and org-scoped Planners, each with its own TOTP mandate.
- **TOTP**: `_require_mfa_for(session, user, roles)` → `_require_mfa_enrolled` → 403 `MFA_REQUIRED` for the first role in `roles` whose mandate is on, called from `require_program_manager`, `require_planner` and both the Program Manager read branch and every `TTXAccess` row of `require_ttx_role` (`security_policy_service.access_mfa_roles`: a team row counts as Planner, plus Evaluator/Observer by its flags). `require_instance_admin` always asks.
- **MFA-pending token**: `create_mfa_pending_token`/`decode_mfa_pending_token` (~5 min) bridges password → TOTP and is never accepted by `get_current_user` or any guard.

## Multi-organization membership
**Every change applies to the context selected in the `ContextBar`** — active organization, exercise and role. Requests carry it explicitly (`/organizations/{activeOrganizationId}/…`, `/ttx/{activeTtxId}/…`, `organization_id` in `POST /ttx`'s body); never add a route or call where the server infers the org or exercise. (A server-resolved `/organizations/planners` once added a Planner to a multi-org Program Manager's *first* org instead of the selected one; all such routes were removed.)

- Roles are never global: the same person can be Player in org A, Planner of B and C, Player in D at once.
- `organization_service.list_user_organizations(session, user)` (`GET /organizations/mine`) = every org the user touches: `OrganizationMembership` orgs ∪ orgs of their `TTXAccess` exercises (covers Player-only orgs). `is_program_manager`/`is_planner` per org come only from `OrganizationMembership`.
- `GET /auth/me`'s `mfa_mandated` (`security_policy_service.mfa_mandated`: any role held anywhere whose mandate is on, or instance administrator) drives the frontend's mandatory-MFA gate; the global `is_program_manager`/`is_planner` are never used for module visibility.
- **Leaving an organization** oneself (`organization_service.leave_organization`, Preferences → Privacy, the active org): every grant goes (tags too) and every exercise seat in that org but a Player's, through the same cascade as a revoke (`_cascade_to_exercises`, Planner then Evaluator then Observer), with the lead successor *chosen* per exercise (`lead_successors`, checked by `check_lead_successor`) instead of the longest-standing one. The last active Program Manager must name a successor among the org's active members whose domain the allowlist accepts for the role (`_program_manager_candidates`, granted with `_add_program_manager`); the default org/context goes if it pointed there. One transaction; the org's name typed (no step-up), recorded as `organization.leave`.
- **Login-time default context**: `User.default_organization_id`/`default_role`/`default_ttx_id`, saved via `PUT /auth/default-context` (`organization_service.set_default_context`, validated against `held_roles_in_organization`; changing the org clears role and exercise). Affects only the *next* login, never the current session. `PATCH /auth/default-organization` still exists (404 for an org the user doesn't belong to) but no screen calls it.

### Frontend active context (`lib/AuthContext.tsx`)
- `activeOrganizationId` and `activeTtxId` (with derived `activeOrganization`/`activeTtx`) are reconciled on every `applySnapshot` (mount and `refresh()`) by `reconcileId()`: keep the current value if still in the freshly fetched list (orgs; the org-filtered `ttxList`), else reseed from `resolveDefaultContext` (`lib/moduleAccess.ts`): saved default, each level falling back to the first available — first org, first role held there (Program Manager > Planner > Controller > Facilitator > Evaluator > Observer > Player), that role's first exercise. A stale or unset default degrades silently.
- `Home()` lands on `routeForContext(resolveDefaultContext(...))`, so the active exercise matches the landing role.
- `setActiveOrganizationId(orgId, ttxId?)` also sets `activeTtxId` in the same call: the given exercise, or (omitted) one reseeded against the new org's exercises. Only the ContextBar's Org segment calls it. It resolves `contextForOrgSwitch` (keep the role being acted as when the new org has it, else that org's first role; that role's first exercise there), then sets the context and navigates to `routeForContext(...)` **inside one `startTransition`**: the router applies navigations as a transition, so a plain state update would render the new org under the old URL, and an old-org exercise route would redirect or `followTtx` back to the old org.
- The exposed `ttxList` is **already filtered to the active org** (raw list internal), so consumers (`ContextBar`, `RequireTtxParam`, Invitations, Pending requests, Enrollments) never deal with multi-org. The mandatory-MFA check is the server's (`mfa_mandated`).
- `getVisibleModules`/`heldRoles` take the active org's summary (`Pick<OrganizationSummary, 'is_program_manager' | 'is_planner'>`): Admin = Program Manager *of the active org*. **One module per role** (`moduleForRole`): Program Manager → Admin, Planner → Creator, Controller → Control, Facilitator / Observer / Evaluator / Player → Execution (the Player landing). `actsAs(ttx, role)` is the client twin of `context_roles()`; `TTXRead` carries `plans`/`controls`/`facilitates`. The acting role is fixed by module, except Execution, where it is the active exercise's: the role picked in the Role selector (`AuthContext.executionRole`, passed to `currentContextRole`) when the exercise allows it — a team member can be its Facilitator, Evaluator and Observer at once — else the first of Facilitator > Evaluator > Observer > Player.
- Preferences → **Default workspace** (`AccountSettingsDefaults`, `/account/settings/defaults`, shown only when `hasContextChoices`) is the only screen saving the default: cascading Organization → Role → Exercise selects that always hold a concrete value (start from `resolveDefaultContext` of the saved default; changing a level reseeds the ones below; a single-option level is disabled; Program Manager saves no exercise) plus a "You'll start in" preview.
